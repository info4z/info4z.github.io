Spring 核心知识

一、基础与入门

（一）Spring 概述

1、什么是 Spring Framework？

Spring 是一个轻量级的 Java 开发框架，旨在简化企业级应用的开发。它最核心的理念是 控制反转（IoC） 和 面向切面编程（AOP）。

  • 狭义 Spring：指 Spring Framework，包含 IoC、AOP、数据访问、Web 等模块。
  • 广义 Spring：指 Spring 生态，包含 Spring Boot、Spring Cloud、Spring Data 等。

2、Spring 的设计哲学

  • 非侵入式：你的业务代码不依赖 Spring 的特定 API。
  • POJO 编程：使用普通的 Java 对象即可，无需继承特定父类或实现特定接口（除非必要）。
  • 模块化：按需引入，不会强制捆绑。

（一）面向切面编程：AOP

1、为什么需要 AOP？

想象一下，你有一个 UserService，里面有 saveUser、deleteUser 等方法。现在要求在每个方法执行前打印日志、执行后统计耗时、出错时发送告警。

每个方法都要重复写这些“非业务”代码，代码冗余、耦合严重、难以维护。AOP 就是把这些横切关注点（Cross-cutting Concerns）抽取出来，统一管理。

2、AOP 核心概念：必须死磕

在 Spring 里，搞懂下面 6 个概念，AOP 就懂了 80%。

graph LR
    A["横切逻辑<br>如：日志、权限"] -->|定义成| B[Aspect 切面]
    B --> C["Advice 通知<br>什么时候执行？"]
    B --> D["Pointcut 切点<br>在哪里执行？"]
    E["目标对象 Target<br>如：UserService"] --> F["Join Point 连接点<br>如：saveUser方法"]
    F -->|Pointcut 匹配到| G["织入 Weaving<br>代理对象生成"]
    G --> H[调用时执行 Advice + 目标方法]
术语 解释（通俗版） 类比
Aspect（切面） 横切逻辑的模块化，就是“你要加的功能”+“加在哪里”的集合。 像一个安全检测员（他负责检查所有入场人员）。
Join Point（连接点） 程序执行过程中所有可以插入代码的点（如方法调用、异常抛出）。在 Spring 中特指方法执行。 场馆的所有入口（每个门口都可以查票）。
Pointcut（切入点） 一组连接点的集合，定义了“到底要在哪几个地方动手”。 通往VIP 包厢的入口（只查这些门口）。
Advice（通知） 在切入点具体执行的动作，即“做什么”+“何时做”。 在 VIP 入口之前查票（Before），或在之后引导入座（After）。
Target（目标对象） 被 AOP 增强（代理）的原始对象。 被检查的真实观众。
Proxy（代理） Spring 为 Target 动态生成的对象，用来执行 Advice。 拿着检测仪的保安（他代替观众去排队）。
Weaving（织入） 把 Advice 应用到 Target 的过程，在 Spring 中是在运行时完成的。 保安正式上岗的那一刻。

3、AOP 底层原理：动态代理

Spring AOP 底层基于代理模式，它根据目标类是否实现接口，自动选择两种代理方式：

graph LR
    A[目标类] --> B{"是否实现接口？"}
    B -->|是| C["JDK 动态代理<br>基于 java.lang.reflect.Proxy"]
    B -->|否| D["CGLIB 动态代理<br>基于字节码增强（子类）"]
    C --> E["代理对象与目标对象<br>实现相同接口"]
    D --> F["代理对象是目标对象的<br>子类（继承）"]
  • JDK 动态代理：要求目标类必须实现接口，代理对象与目标对象是兄弟关系（同一接口）。
  • CGLIB 动态代理：目标类无需接口，通过继承目标类生成子类作为代理，不能代理 final 类和方法。

在 Spring Boot 2.x/3.x 中，默认配置下，如果目标类有接口，优先使用 JDK 代理；如果没接口，则用 CGLIB。我们可以强制要求使用 CGLIB（@EnableAspectJAutoProxy(proxyTargetClass = true)）。

4、通知（Advice）的五种类型

这是 AOP 编码最核心的部分。Spring 支持 AspectJ 的注解风格。

注解 执行时机 能否控制目标方法执行
@Before 目标方法执行之前 ❌ 不能，只能做前置操作
@AfterReturning 目标方法正常返回之后 ❌ 不能

@Around 环绕目标方法执行（最强） ✅ 能（通过 proceed() 控制）

7、AOP 的实战最佳实践

  1. 谨慎使用 @Around：因为它最强，也最容易出问题（忘记调用 proceed() 会导致业务不执行）。
  2. 切面类尽量无状态：避免在切面中定义成员变量，除非是线程安全的。
  3. 避免切面调用自身：如果切面内部方法调用，不会触发代理，要使用 AopContext 获取代理对象。
  4. 性能考量：AOP 是代理模式，会增加方法调用的开销（通常可忽略，微秒级）。

5、传播行为：Propagation —— 最重要！

当 事务方法被另一个事务方法调用 时，当前事务该如何处理？这就是传播行为。

传播行为 含义（核心） 实战场景
REQUIRED（默认） 如果当前有事务，就加入；没有就新建一个。 90% 的业务场景（增删改）
REQUIRES_NEW 无论当前有无事务，都挂起当前事务，新建一个独立事务。 操作日志、审计日志（必须独立保存）
NESTED 如果当前有事务，创建嵌套事务（保存点）；没有则新建。 批量处理，部分失败部分回滚
SUPPORTS 如果有事务就加入，没有就以非事务执行。 查询方法（可读但宽松）
NOT_SUPPORTED 以非事务执行，如果当前有事务则挂起。 非关键操作
MANDATORY 必须存在事务，否则抛异常。 强制事务环境（极少用）
NEVER 必须不在事务中，否则抛异常。 禁止事务（极少用）

6、隔离级别：Isolation

隔离级别解决并发事务的脏读、不可重复读、幻读问题。

隔离级别 脏读 不可重复读 幻读 说明
READ_UNCOMMITTED ✅ ✅ ✅ 最低级别，性能最高，安全性最差
READ_COMMITTED ❌ ✅ ✅ Oracle 默认，防止脏读
REPEATABLE_READ ❌ ❌ ✅ MySQL 默认，防止脏读和不可重复读
SERIALIZABLE ❌ ❌ ❌ 最严格，串行执行，性能最低

通常情况下，我们保持 Isolation.DEFAULT，即使用数据库自身的隔离级别（MySQL 默认 Repeatable Read，Oracle 默认 Read Committed）。

7、@Transactional 失效的 5 大陷阱 —— 必看面试/实战重点

（1）同一个类中，方法内部调用（自调用）导致失效

解决方案

或者利用 AopContext.currentProxy()（需开启 exposeProxy=true）。

（2）异常被内部捕获，未抛出给代理

解决：在 catch 中手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(); 或重新抛出异常。

（3）非 RuntimeException 默认不会滚

Spring 默认只对 RuntimeException 和 Error 回滚。如果抛出 IOException（检查型异常），事务不会滚。

（4）@Transactional 只能用在 public 方法上

Spring 的 AOP 代理限制（CGLIB/JDK）只会拦截 public 方法。protected 或 private 上的注解被忽略（不报错，但没效果）。

（5）表引擎不支持事务（如 MySQL 的 MyISAM）

数据库引擎问题，记得使用 InnoDB。

8、只读事务（readOnly = true）

对于纯粹的查询方法，建议显式标记为只读。

作用：

  1. 优化提示：告诉数据库驱动或 Hibernate，不需要开启事务日志（提高性能）。
  2. 预防误操作：如果方法内意外执行了 update，有些实现会抛出异常（非强制）。

2、WebSocket 与 STOMP 的关系

WebSocket 是一个 底层传输协议（类似于 TCP）。如果我们直接使用原生的 WebSocket，消息格式需要自己定义（比如 JSON 字符串），缺乏路由、订阅、点对点等高级功能。

STOMP（Simple Text Oriented Messaging Protocol） 是运行在 WebSocket 之上的 子协议（类似于 HTTP 是 TCP 之上的协议）。它定义了一套消息格式（SEND、SUBSCRIBE、MESSAGE 等帧），让我们可以用 “订阅/发布” 的模式来管理消息。

SockJS：为了解决老旧浏览器不支持 WebSocket 的问题，Spring 提供了 SockJS 支持。它可以自动降级到轮询等方案，保证兼容性。

（二）缓存抽象：Cache Abstraction

1、为什么需要缓存抽象？

在业务系统中，我们经常遇到这样的场景：

缓存的本质：将高频读取、低频变化的数据（如商品信息、用户权限）暂存在内存（如 Caffeine、Redis）中，下次再请求时直接从内存返回，从而大幅降低数据库压力，提升响应速度。

Spring 的缓存模块并非一个具体的缓存实现（如 Redis 或 Ehcache），而是一套统一的编程模型。你可以随时切换底层缓存技术，而业务代码中的 @Cacheable 注解无需任何改动。

8、缓存三大陷阱及解决方案 —— 面试高频

（1）缓存穿透：查询不存在的数据

  • 问题：大量请求查询一个不存在的 ID（如 -1），每次都穿透到数据库。

  • 解决：unless = "#result == null" 不缓存 null 会导致穿透。

优化：缓存一个空对象（new Product()）或特定标识，设置短期过期时间。

（2）缓存击穿 —— 热点 Key 过期

  • 问题：某个极其热门的商品（如 iPhone 秒杀）缓存失效瞬间，大量请求同时打到数据库。
  • 解决：使用 sync = true（加锁，只让一个线程查库）。

（3）缓存雪崩 —— 大面积过期

  • 问题：大量缓存同时过期（如 10 分钟统一过期），导致瞬间流量压垮数据库。
  • 解决：设置不同的过期时间（随机偏移），或使用 Caffeine 的 expireAfterWrite 结合固定 + 随机值。

本节思考

  1. @Cacheable 方法如果内部抛出了异常，缓存会怎么处理？（提示：不会缓存，正常业务异常对外抛出）
  2. 如果 @Cacheable 和 @CachePut 同时标注在一个方法上会怎样？（提示：@Cacheable 会因 @CachePut 总是执行而导致缓存读取失效，通常不建议混合）
  3. 在分布式微服务场景下，本地缓存（Caffeine）有什么致命缺陷？该如何解决？（提示：数据不一致。解决：使用集中式缓存 Redis，或配合消息总线广播失效事件）

单元测试：测试单个类或方法，不依赖 Spring 容器（使用 Mockito 即可）。

集成测试：测试多个 Bean 的协作（如 Service + DAO），需要加载 Spring 容器，但不启动 Web 服务器，通过 MockMvc 模拟 HTTP 请求。

Spring 的测试框架：让集成测试变得极其优雅，支持容器缓存（多个测试类共享同一个容器，大幅提速）和事务自动回滚（防止污染数据库）。

7、常用测试注解速查表

注解 作用 适用场景
@ExtendWith(SpringExtension.class) 将 Spring 测试框架与 JUnit 5 桥接 集成测试必备
@ContextConfiguration 指定配置文件或配置类 指定加载哪些 Bean
@Transactional 测试方法在事务中执行，默认回滚 数据库测试（防污染）
@Sql 测试前后执行 SQL 脚本 初始化/清理数据
@WebAppConfiguration 声明 ApplicationContext 是 Web 类型 MVC 测试
@MockBean 在容器中创建 Mock 对象替换原 Bean 模拟外部依赖
@AutoConfigureMockMvc 自动配置 MockMvc Controller 测试（Boot 专属）
@TestPropertySource 覆盖测试环境的配置属性 修改端口、数据库地址等

本节思考

  1. 单元测试 vs 集成测试：单元测试用 @ExtendWith(MockitoExtension.class)，集成测试用 @ExtendWith(SpringExtension.class)。两者目标不同，不要混用。
  2. 测试上下文缓存：ApplicationContext 在测试套件中是全局缓存的。所以即使有 100 个测试类，只要配置相同，容器只启动一次，这是 Spring 测试极快的秘密。
  3. @DirtiesContext：如果你的测试修改了容器状态（如改变系统属性），可以用 @DirtiesContext 标记该测试类，Spring 会在该测试后重置容器（但代价是下次重新加载，影响性能，慎用）。
