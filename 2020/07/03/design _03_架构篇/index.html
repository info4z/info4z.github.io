架构篇

现在我们进入第三部分：架构篇——设计模式在系统架构中的交响。前面两部分的模式大多在单个进程内发挥作用，而架构模式则是在更高的层次上组织整个系统，指导我们如何划分模块、定义通信、处理数据流。它们与前文的设计模式紧密相关，是模式思想的规模化应用。

第9章 架构模式：更高层的设计模式

9.1 分层架构：经典与演进

分层架构是最基础的架构模式，通过水平分层将系统划分为：表示层、业务逻辑层、数据访问层（有时还有服务层、基础设施层）。核心原则是上层依赖下层，下层不感知上层。

经典三层示例（Spring Boot）

依赖关系图：

graph TD
    subgraph 表示层
        Controller
    end
    subgraph 业务层
        OrderService
    end
    subgraph 数据层
        OrderRepository
    end
    Controller --> OrderService
    OrderService --> OrderRepository

传统分层的不足：

  • 依赖朝下，但业务层直接依赖数据层的接口（OrderRepository）还算合理，但如果业务层不慎引入了 @Entity 注解的 JPA 实体，就会耦合具体 ORM 框架，违反 DIP。
  • 当需求变化时，往往需要从下往上改，比如换个数据库，可能影响业务层。

依赖倒置改进：DDD 分层

领域驱动设计提倡倒置依赖：领域层不再依赖基础设施，而是基础设施依赖领域。我们定义仓储接口在领域层，具体实现在基础设施层，完全符合六边形架构思想。

依赖方向：Controller → OrderService（领域） → OrderRepository（领域接口） ← JpaOrderRepository（基础设施）。这使领域保持纯粹，便于测试和替换。

9.2 六边形架构（端口与适配器）

六边形架构（也称端口与适配器架构）是微服务中保持核心领域独立性的利器。它的核心思想是：

  • 领域位于中心，对外定义端口（接口）。
  • 外部依赖（HTTP、数据库、消息队列）通过适配器实现端口，与领域交互。

9.3 CQRS（命令查询职责分离）与事件溯源

CQRS 将操作分为命令（写）和查询（读），使用不同的模型甚至不同的数据库。这能极大提升复杂业务系统的性能、可扩展性和灵活性。

核心思想：

  • 命令端：处理业务流程，保证不变性，使用优化的写模型（如标准化的关系表）。
  • 查询端：面向展示优化，可能使用宽表、搜索索引、缓存或 NoSQL。

简单实现（同数据库，不同模型）：

当查询模型独立数据库时，命令处理完毕后发布事件，事件处理器更新查询数据库：

sequenceDiagram
    participant Client
    participant CommandAPI
    participant WriteDB
    participant EventBus
    participant EventHandler
    participant ReadDB
    Client->>CommandAPI: POST /orders
    CommandAPI->>WriteDB: insert order
    CommandAPI->>EventBus: publish OrderCreated
    EventBus->>EventHandler: on OrderCreated
    EventHandler->>ReadDB: update order_summary_view

事件溯源（Event Sourcing）：不保存当前状态，只保存状态变化的全部事件序列。当前状态由事件重放得出。非常适合审计、回溯、并发冲突解决，但增加复杂性。

架构决策：CQRS 带来了最终一致性、额外维护成本，但能解决复杂的报表、多客户端差异化查询、高并发读写冲突。事件溯源适合高审计、复杂状态重建场景，通常与 CQRS 搭配。

9.4 微服务拆分的模式：按业务能力、子域、事务边界

微服务不是越细越好，关键是要找到正确的边界。DDD 提供了强大的拆分指导：

  • 限界上下文：一个业务领域的边界，内部有统一的模型。
  • 聚合：事务一致性的基本单位，跨聚合需通过事件最终一致。

拆分模式：

  1. 按业务能力：订单服务、支付服务、库存服务，每个服务对应一个业务功能。
  2. 按子域：核心域（企业核心竞争力，如电商的推荐算法）、支撑子域（如物流）、通用子域（如用户认证，可用标准产品）。
  3. 按事务边界（聚合）：一个微服务至少包含一个聚合，避免跨聚合的强一致性。

例子：电商系统的拆分

架构原则：

  • 服务内高内聚，服务间松耦合。
  • 避免分布式单体：不要仅仅把原本的内部方法调用换成 RPC，而忽略服务独立部署和数据库独立。
  • 逐步拆分（绞杀者模式），而不是一次性重写。

9.5 管道-过滤器：ETL、数据流与无服务器架构

管道-过滤器模式将任务分解为一系列处理步骤（过滤器），通过管道连接，每个过滤器独立、可重用。

Unix 管道：cat log.txt | grep "ERROR" | sort | uniq -c

Java 8 Stream 体现：

架构实例：ETL 管道（数据清洗、转换、加载）

在 Spring Cloud Data Flow 或 Apache Camel 中，管道-过滤器是核心模式。无服务器（AWS Step Functions / Lambda）中，每个函数是一个过滤器，通过事件串联。

架构图：

graph LR
    A[数据源] --> B[过滤器: 验证]
    B --> C[过滤器: 转换]
    C --> D[过滤器: 丰富]
    D --> E[过滤器: 存储]
    E --> F[目标]

与责任链的区别：管道-过滤器通常每个过滤器都会修改数据并传递给下一个，且管道可以分支、汇聚；责任链则主要用于决定“谁处理请求”，可能中途终止。

第9章小结：从分层到六边形，从 CQRS 到微服务拆分，再到管道-过滤器，这些架构模式都离不开我们前文学习的设计原则和具体模式。六边形架构重度使用适配器和外观，CQRS 可结合策略模式处理命令验证，微服务拆分要求深刻理解单一职责和依赖倒置，管道-过滤器则是责任链和装饰器的变体放大版。

第10章 分布式系统模式

10.1 服务发现与负载均衡

在微服务中，服务实例动态变化（扩缩、故障、部署），客户端无法硬编码地址。服务发现解决“如何找到服务”的问题。

两种模式：

  • 客户端发现：客户端查询服务注册表（如 Eureka, Consul），自行选择实例并负载均衡。Spring Cloud LoadBalancer 即是此类。
  • 服务端发现：客户端请求经负载均衡器（如 Nginx, Envoy），由负载均衡器查询注册表并转发。

10.2 断路器模式：防止级联故障

当依赖服务失败或响应缓慢时，如果不加控制，调用方线程会阻塞耗尽资源，导致故障蔓延。断路器（Circuit Breaker）监控调用状态，当失败率超过阈值时“跳闸”，直接拒绝请求一段时间，给下游恢复空间。

架构应用：

  • 网关层断路器：Spring Cloud Gateway 集成 Resilience4j，对每条路由配置。
  • 服务间调用的标准容错模式。
  • 需配合超时设置，防止断路器迟迟不打开（慢响应拖垮线程）。

注意事项：断路器记录失败和成功，要保证调用的读写分类（查询失败不应导致打开，或许只触发降级），且需定义好 fallback 返回（缓存值、默认值、降级逻辑）。

10.3 舱壁模式与重试、退避、幂等

10.3.1 舱壁模式（Bulkhead）

将系统资源（线程池、连接池）分隔成多个隔离的舱室，一个服务的问题不会耗尽所有资源。

Resilience4j 实现线程池隔离：

与信号量舱壁：线程池隔离较重，信号量隔离轻量但无法处理阻塞调用的线程占用。根据场景选择。

10.3.2 重试与退避

瞬时故障（网络闪断、临时不可用）可通过重试解决。但重试需小心：不重试非幂等操作、要设定最大重试次数、使用退避延迟避免加重下游压力。

退避策略：第一次重试等 500ms，第二次等 1000ms，第三次等 2000ms。防冲突，可加随机因子（抖动）。

10.3.3 幂等性

重试可能导致同一操作执行多次，因此写操作必须幂等。实现方式：

  • 幂等键：客户端生成一个唯一键（如订单ID），服务端检查是否已处理。
  • 数据库唯一约束：插入时利用主键或唯一索引防重。

在消息队列消费端，手动提交偏移量并记录消费处理完成，保证 at-least-once + 幂等 = exactly-once 效果。

10.4 边车模式、大使模式与 API 网关

10.4.1 边车模式 (Sidecar)

在容器化环境中，为每个应用容器部署一个辅助容器（边车），提供通信、监控、安全等功能。服务网格（如 Istio）通过边车代理（Envoy）实现了客户端服务发现、负载均衡、断路器、度量收集等，无需修改应用代码。

架构图：

graph TD
    subgraph Pod A
        AppA[应用容器 A]
        SidecarA[Envoy 代理 A]
    end
    subgraph Pod B
        AppB[应用容器 B]
        SidecarB[Envoy 代理 B]
    end
    AppA --> SidecarA
    SidecarA -->|mTLS 负载均衡| SidecarB
    SidecarB --> AppB

架构价值：将网络函数从应用剥离，实现跨语言统一治理。架构师需评估引入服务网格的复杂度，一般中大型系统才收益明显。

10.4.2 大使模式 (Ambassador)

大使是客户端代理，辅助主应用访问外部服务。例如，应用使用 Redis 时，配一个 Redis 大使做分片、监控、加密。

边车是“近身辅助”，大使是“对外特使”，有时两者概念接近，但意图不同：大使对外部调用的一揽子处理。

10.4.3 API 网关

API 网关是系统统一入口，提供路由、聚合、认证、限流、监控等功能。它是外观模式在系统边界的应用。

本章总结：分布式系统模式的实现从 Spring Cloud / Resilience4j 到 Kubernetes / Istio，抽象层次不断提升，但思想一致——管理不可靠的网络，隔离故障，保证最终一致。架构师要熟稔这些模式，在不同基础设施成熟度下做出最佳匹配。

第11章 企业集成模式

企业集成模式（EIP）由 Gregor Hohpe 和 Bobby Woolf 总结，为消息系统提供了一整套设计词汇。我们通过 Spring Integration、Apache Camel 或 Kafka Streams 的实现来理解它们。

11.1 消息通道与消息路由器

消息通道（Message Channel）

通道是消息传递的虚拟管道，解耦发送者和接收者。点对点通道（Queue）保证一条消息只被一个消费者消费；发布-订阅通道（Topic）广播给所有订阅者。

Kafka 实现：Topic 提供发布-订阅，分区实现点对点（同一分区内有序，消费者组内竞争消费）。

JMS 或 RabbitMQ 中，通过 Queue（点对点）和 Topic（发布-订阅）来实现。

消息路由器（Message Router）

路由器根据消息内容或规则，决定目标通道。它是策略模式在消息空间的体现。

内容路由器（Content-Based Router）：根据消息类型路由。

Kafka Streams 分支：将流分流。

架构图：

graph TD
    A[Order Input] --> B{Content Router}
    B -->|amount > 1000| C[highValueChannel]
    B -->|其他| D[normalChannel]
    C --> E[VIP 处理]
    D --> F[标准处理]

其他路由器变体：

  • Message Filter：丢弃不符合条件的消息（如过滤掉测试订单）。
  • Dynamic Router：运行时决定路由路径。
  • Recipient List：向一组接收者发送（如通知多部门）。

11.3 聚合器、分离器与分散-收集

这些模式将消息拆分和重组，以处理复杂的业务流程。

分离器（Splitter）

将一条包含多个项的消息拆分成多条独立消息，然后分别处理。

订单包含多个商品行项目，需要分别检查库存。

类图示意：

graph LR
    A[订单消息] --> B[Splitter]
    B --> C1[商品A消息]
    B --> C2[商品B消息]
    B --> C3[商品C消息]

聚合器（Aggregator）

与分离器相对，聚合器接收多条相关消息，合并成一条。需定义关联 ID 和完成条件（所有部分到齐或超时）。

所有库存检查结果返回后，聚合为订单确认。

聚合器状态图：

stateDiagram-v2
    [*] --> Collecting
    Collecting --> Collecting : 接收部分结果
    Collecting --> Complete : 所有结果到达
    Collecting --> Timeout : 超时
    Complete --> [*]
    Timeout --> [*] : 发送超时错误

分散-收集（Scatter-Gather）

综合分离器和聚合器：将请求分散到多个接收者，然后将它们的响应聚合为一个结果。常见于从多个服务获取数据拼装视图。

11.4 死信通道与补偿事务

死信通道（Dead Letter Channel）

当消息无法被正确处理（消费失败、路由失败）时，将其发送到死信通道，避免阻塞主流程，并供后续人工或自动处理。

Kafka 中利用死信 topic：

RabbitMQ 可以通过拒绝且不重新入队，配合死信交换器实现。

架构中，死信队列的消息需要监控和告警，运维可查看并重试或修复。

补偿事务（Compensating Transaction）

在 Saga 模式中，分布式事务采用补偿来实现最终一致性。每个步骤成功后执行正向操作，失败时执行补偿动作回滚已成功的步骤。

架构图（Saga 流程）：

sequenceDiagram
    participant Order
    participant Inventory
    participant Payment
    Order->>Order: 创建订单(pending)
    Order->>Inventory: 事件: OrderCreated

    end

架构决策：编排式 Saga 简单、无中心协调器，但流程复杂时监控困难；指挥式 Saga（Orchestration）用中心 Saga 管理器统一调度，清晰但略重。补偿操作需实现幂等，因为重试或网络问题可能造成重复补偿。

本章总结：消息通道、路由器、转换器构成了消息传递的基础设施。分离器与聚合器、分散-收集处理消息的合并与拆分，支撑复杂的数据流。死信通道和补偿事务则为异常和最终一致性提供了保障。所有这些模式共同组成了现代异步微服务架构的神经系统。

我们进入第12章：领域驱动设计中的战术模式。DDD 不仅关乎战略设计（限界上下文、上下文映射），更提供了一套战术模式，用于在单个限界上下文内构建富有表达力、能捕捉业务规则的领域模型。它们与之前所学的设计模式深度融合，是微服务内部结构的核心。

第12章 领域驱动设计中的战术模式

12.1 实体与值对象：建模身份与特征

实体（Entity）：拥有唯一标识，贯穿生命周期，其变化会被追踪。例如订单、用户、车辆。

值对象（Value Object）：没有标识，通过其属性定义相等性，通常不可变。例如金额、地址、颜色。

代码示例：订单聚合中的实体与值对象

类图：

classDiagram
    class Order {
        -orderId: String
        -totalAmount: Money
        -status: OrderStatus
        +create(orderId, items) Order
        +pay()
    }
    class Money {
        -amount: BigDecimal
        -currency: Currency
        +add(Money) Money
    }
    class OrderItem {
        -productId: String
        -price: Money
        -qty: int
    }
    Order *-- Money : totalAmount
    Order *-- OrderItem : items

架构视角：

  • 实体应该内聚业务行为，而不只是数据持有者（贫血模型）。pay() 方法封装了状态变更逻辑和保护。
  • 值对象让领域概念显式化，避免基础类型滥用（如 BigDecimal 和 String 满天飞）。DDD 强调用类型系统消除歧义。

12.2 聚合与聚合根：保证业务不变量

聚合是一个事务一致性的边界，由一个聚合根（实体）控制，外部只能通过聚合根访问内部实体。聚合根确保每次业务操作只在一个事务内修改一个聚合。

订单聚合设计：

  • 聚合根：Order，包含订单项集合（List<OrderItem>）。
  • 业务规则：订单总金额必须等于订单项金额之和，支付前状态必须为待支付。
  • 不允许直接修改 OrderItem，所有操作都通过 Order 根。

原则：

  • 小聚合优于大聚合，以事务一致性为边界。当需要跨聚合一致性时，采用最终一致性和领域事件。
  • 聚合间引用通过标识而非对象引用（如订单中的 userId 字符串，而非 User 对象），避免懒加载问题与边界模糊。

12.3 仓储与工厂：管理聚合生命周期

仓储（Repository）：为聚合提供持久化和检索的抽象，隐藏底层存储细节。它属于领域层的端口。

工厂：封装复杂创建逻辑，隔离创建细节。在领域层，工厂方法或独立工厂类保证创建出的聚合始终满足不变量。

架构要点：

  • 仓储接口定义在领域层，实现在基础设施层，完全符合六边形架构。
  • 工厂不是 GoF 的创建型模式简单套用，而是为了封装复杂的、跨聚合的创建逻辑，甚至调用防腐层（如检查客户状态）。

12.4 领域服务与领域事件

当业务操作不属于任何一个实体或值对象时，声明为领域服务。领域服务是无状态的，表达跨实体或跨聚合的业务流程。

领域服务示例：转账服务

领域事件：领域内发生的重要事情，用事件对象表示，并在聚合间通信。

在应用服务或领域服务中，完成聚合持久化后，收集所有领域事件并发布到事件总线。

架构关系图：

graph TD
    subgraph 领域层
        Entity[实体/聚合]
        VO[值对象]
        DS[领域服务]
        DE[领域事件]
    end
    subgraph 应用层
        AppService[应用服务]
    end

    EventBus -.->|实现| EventInterface

架构决策：

  • 领域事件使跨聚合、跨限界上下文的通信解耦，易于实现最终一致性。
  • 不要使用静态的事件发布器，应通过应用服务协调，保持聚合纯净。

12.5 规约模式（Specification）

规约将业务规则封装为可复用的对象，并可组合（AND, OR, NOT）。它主要用于：

  • 验证对象是否满足条件。
  • 从集合中筛选对象。
  • 查询条件构建（需与仓储配合）。

规约接口与实现：

架构视角：

  • 规约将业务规则从实体中分离，使得规则本身可复用、可测试，并易于修改。
  • 在仓储中，可将规约转换为底层查询（如 JPA Criteria API），但要注意泄露基础设施细节，需权衡。
  • 规约模式是策略模式在规则验证上的特化，体现了开闭原则和单一职责。

本章小结：DDD 战术模式从微观上规定了领域模型的组织方式。实体与值对象丰富业务语义，聚合与聚合根定义事务边界与不变量，仓储与工厂管理生命周期，领域服务、领域事件、规约解决无主逻辑和跨边界通信。它们与前文的设计模式高度呼应：仓储是外观/适配器，领域事件是观察者/发布-订阅，规约是策略模式的分支。
