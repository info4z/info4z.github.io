第4章 依赖治理：反转与控制

依赖管理是架构的核心。如果依赖方向混乱，任何模块化、可测试性、可维护性的努力都将事倍功半。本章从工厂模式家族出发，一直演进到现代的依赖注入，并审视服务定位器这一备受争议的模式。

4.1 依赖倒置原则 (DIP) 与依赖注入 (DI)：从原则到模式

回顾第2章讲过的 DIP：高层模块不应依赖低层模块，两者都应依赖抽象。但原则只告诉“应该怎样”，并没有说“如何做到”。依赖注入就是实现 DIP 的一种具体手段。

三种常见的注入方式：

  1. 构造函数注入（推荐）：强制依赖在创建时提供，不可变。
  2. Setter 注入：可选依赖，运行时可变。
  3. 接口注入：不常见，Spring 中有 InitializingBean 之类。

4.2.4 从工厂到 DI 容器

手动工厂无法应对对象依赖图爆炸的情况。现代 DI 容器（Spring IoC, Guice, Dagger）本质上是一个超级工厂，它能：

  • 自动发现 Bean（通过注解或 XML）
  • 解析依赖图（如果一个 Bean A 需要 B，B 需要 C，容器自动创建 C，再创建 B，再创建 A）
  • 管理生命周期（单例、原型、请求作用域等）

架构决策：DI 容器虽然强大，但会引入框架依赖和一定的性能开销（启动时扫描、反射）。对于极其轻量的组件，可能手动 DI 更合适。但在中大型项目中，DI 容器的收益远大于成本。同时要注意：容器不是用来绕开 DIP 的工具，不要在业务代码中频繁通过容器 API 获取 Bean（这就会滑入服务定位器反模式）。

4.3 服务定位器模式及其在架构中的争议

服务定位器是另一种获取依赖的方式：每个对象通过一个众所周知的注册表来查找所需的依赖。

看起来很方便，为什么饱受争议？

  1. 隐藏依赖关系：看 OrderService 的签名，你完全不知道它依赖 OrderRepository。必须阅读代码内部才能了解。
  2. 违反 DIP：OrderService 直接依赖 ServiceLocator 这个具体工具类，而不是依赖抽象。
  3. 测试困难：测试时必须设置全局的服务定位器，容易产生测试之间的耦合。
  4. 运行时错误：如果忘记注册某个依赖，到运行期解析时才抛异常，而不是构造期就发现。

但是，服务定位器在某些架构中仍有一席之地：

  • 遗留系统集成：难以完全重构到 DI 时，服务定位器可以作为“提供抽象”的第一步。
  • 框架内部实现：很多 DI 容器内部使用服务定位器模式（如 Spring 的 BeanFactory.getBean()），但不应该暴露给业务代码。
  • 插件架构：插件通过定位器获取宿主服务。

架构师的处理原则：将服务定位器限定在基础设施层，并严格规定业务代码禁止直接调用。更好的方式是对其再封装，通过“领域服务”提供清晰的 API，内部使用定位器，但对外表现为显式依赖。其实，现代的 JNDI、OSGi 服务注册也带服务定位器影子，关键看你怎么用。

本章总结

模式 核心思想 架构适用度

依赖治理的最高境界：业务代码中没有 new，也没有 ServiceLocator.resolve，所有对象都在启动时装配完成，依赖方向指向领域核心。这就是依赖注入与六边形架构结合时的完美图景。

第5章 接口与边界：隔离变化的第一道防线

架构的本质是划清边界，边界的一侧是稳定的核心逻辑，另一侧是多变的外部依赖（数据库、UI、第三方系统）。设计模式中的适配器、外观、代理、桥接正是构建这些边界的主力。

5.1 适配器模式：集成与防腐

当我们需要集成一个已有组件，但其接口与系统内部要求的接口不匹配时，适配器负责转换。在领域驱动设计中，这被称为防腐层（Anti-Corruption Layer），它的使命就是阻止外部模型“污染”内部领域模型。

场景：统一支付网关。内部系统期望一个 PaymentProcessor 接口，但支付宝、微信各自的 SDK 接口完全不同。

架构视角：

  • 防腐层的实践：适配器内部持有外部 SDK 对象，所有类型转换、异常转换都在这里完成。一旦更换第三方，只需重写一个适配器，核心领域 PaymentService 零改动。
  • 类适配器 vs 对象适配器：Java 中我们多用对象适配器（组合），因为它更灵活，可以适配一个类的多个子类。类适配器（多继承）在单继承的 Java 中较少使用。
  • 与外观的区别：适配器解决接口不匹配；外观是简化接口。

5.2 外观模式：统一入口，隐藏复杂度

在微服务架构中，API 网关就是最典型的外观。它为客户端提供一个简单、统一的入口，隐藏背后几十个服务的复杂性。

示例：一个 OrderFacade 负责下单流程，内部需要调用库存服务、支付服务、物流服务，并提供聚合后的结果。

序列图（同步调用）：

sequenceDiagram
    participant Client
    participant OrderFacade
    participant InventoryService
    participant PaymentService
    participant ShippingService
    Client->>OrderFacade: POST /orders
    OrderFacade->>InventoryService: check(sku, qty)
    InventoryService-->>OrderFacade: true
    OrderFacade->>PaymentService: pay(orderId, total)
    PaymentService-->>OrderFacade: success
    OrderFacade->>ShippingService: schedule(orderId, addr)
    ShippingService-->>OrderFacade: ok
    OrderFacade-->>Client: 200 OK

架构决策要点：

  • BFF（Backend for Frontend）：为每种客户端（Web、Mobile）提供专门的外观层，聚合出最适合该客户端的视图，进一步减少请求次数和数据冗余。
  • 避免上帝外观：不要把所有业务流程都塞进一个外观，这会让外观变成新的“大泥球”。应按限界上下文或业务能力拆分多个外观。
  • 同步与异步：如果下单流程中某些步骤（如发送通知）不需要即时返回结果，可以在外观中改为发送事件，解耦并提升响应速度。

5.3 代理模式：透明地介入控制

代理提供一个对象的替身，以控制对这个对象的访问。常见变体：远程代理（RMI）、虚拟代理（延迟加载）、保护代理（权限检查）。AOP（面向切面编程）正是基于动态代理实现的。

示例：保护代理，控制对文档编辑器的访问。

架构应用：

  • AOP 横切关注点：Spring AOP 基于动态代理实现了声明式事务、缓存、权限。
  • 延迟加载：Hibernate 的懒加载集合使用代理，等到真正访问时才从数据库加载。
  • 远程代理：gRPC/RMI 的客户端存根，使得调用远程服务就像调用本地方法。

与装饰器的区别：代理旨在控制访问（权限、延迟、远程），装饰器旨在增强功能（添加新行为）。尽管结构相似，但意图不同。

5.4 桥接模式：分离抽象与实现，应对多维变化

当系统在两个或多个独立维度上频繁变化时，桥接模式将抽象部分与实现部分分离，让它们可以独立变化。

经典案例：JDBC 体系。JDBC 定义了 Connection、Statement 等抽象接口，各数据库厂商提供具体的 Driver 实现。应用程序只依赖抽象接口，可以在不修改代码的情况下切换数据库。

这里的 DriverManager 配合具体的 Driver（如 com.mysql.cj.jdbc.Driver）就是桥接的实现部分。维度一是“数据库操作 API”（Connection, Statement），维度二是“具体数据库实现”（MySQL Driver, PostgreSQL Driver）。

架构场景：消息中间件抽象。

假设系统初期使用 RabbitMQ，中期需要迁移到 Kafka。如果不做抽象，业务代码到处是 RabbitMQ 特定的代码。通过桥接，抽象出 MessageProducer 和 MessageConsumer，再为每种中间件提供实现。

类图：

classDiagram
    class MessagingBridge {
        <<interface>>
        +publish(topic, message)
        +subscribe(topic, handler)
    }
    class RabbitMQMessagingBridge {
        +publish(topic, message)
        +subscribe(topic, handler)
    }
    class KafkaMessagingBridge {
        +publish(topic, message)
        +subscribe(topic, handler)
    }
    class OrderEventPublisher {
        -bridge: MessagingBridge
        +orderCreated(order)
    }
    MessagingBridge <|.. RabbitMQMessagingBridge
    MessagingBridge <|.. KafkaMessagingBridge
    OrderEventPublisher --> MessagingBridge

与策略模式的区别：

  • 策略：封装一组可互换的算法，运行时动态切换。如支付策略：支付宝、微信。意图是行为选择。
  • 桥接：分离抽象与实现，使得两者可以独立演化。上例中，抽象（事件发布逻辑）和实现（具体消息中间件）可以独立变化，比如加一个 RocketMQ 实现，或增加一种新的发布抽象（带事务消息），互不影响。

架构价值：桥接可以防止因多维变化导致的“类爆炸”，并允许你在不改变高层逻辑的情况下，替换底层的技术实现。它非常适合用于构建平台抽象层。

本章小结：

模式 目的 关键边界 架构角色
适配器 接口转换 内部领域与外部系统 防腐层、集成第三方
外观 简化复杂系统接口 客户端与后台服务 API网关、BFF
代理 控制对象访问 调用方与被调用对象 AOP、延迟加载、远程调用

这些模式围绕一个核心思想：对内保护稳定，对外隔离变化。它们是架构师画边界线时最常用的工具。

6.2 模板方法模式：骨架统一，细节可定制

模板方法定义一个操作的骨架，将某些步骤延迟到子类。框架设计中无处不在，例如 HttpServlet.service() 调用 doGet、doPost。

架构场景：数据同步框架。从多种数据源同步数据，流程固定：连接→提取→转换→加载→记录日志→断开连接，但具体步骤不同。

类图：

        +sync()

        #transform(List~RawData~) List~TransformedData~
        #load(List~TransformedData~)
        #logSync()
        #disconnect()
    }
    class MySQLSync {
        +connect()
        +extract()
        +transform(...)
        +load(...)
    }
    class MongoDBSync {
        +connect()
        +extract()
        +transform(...)

    DataSyncTemplate <|-- MongoDBSync

架构要点：

  • 好莱坞原则：Don’t call us, we’ll call you。框架控制流程，调用子类实现。
  • 钩子方法：提供可选扩展点，避免子类必须实现所有步骤，增强了灵活性。
  • 在微服务框架中的应用：例如 Spring Batch 的 Job/Step 处理流程，或 API 网关中的请求处理管道，都大量运用模板方法模式。

技术总监警示：模板方法容易造成继承层次过深、类膨胀。优先考虑使用组合/策略模式替代部分步骤，特别是当“骨架”本身也需要演化时。

从观察者到事件驱动架构的演化：

  • 发布-订阅：进程外，异步，适合微服务。

  • 同步观察者可能拖慢主流程，但一致性强。
  • 异步发布-订阅提升吞吐，但需处理最终一致性、消息丢失、重复消费。引入事务发件箱模式保证事件可靠发布。

6.4 责任链模式：灵活的中间件与工作流

在 Web 框架中，请求穿过一系列过滤器/拦截器，每个都有权终止流程或继续传递。这就是责任链。

Netty 风格的简单实现：

这就是责任链模式在现代微服务网关中的最佳实践：声明式链式处理，可通过配置动态调整过滤器顺序和参数，极大提升系统的灵活性。

架构师需注意：

  • 链中某个处理器如果没有继续调用 chain.doFilter，会导致链中断，需谨慎设计。
  • 长链可能影响性能，需要合并或异步化。
  • 责任链非常适合实现管道-过滤器架构，在 ETL、数据流处理中也是核心模式。

模式 意图 架构应用
策略 封装可互换算法 规则引擎、可插拔定价、验证器
模板方法 固化算法骨架，定制步骤 数据同步框架、批次处理
观察者/发布-订阅 一对多通知解耦 事件驱动架构、微服务异步通信

所有这些模式都服务于让系统行为可以独立于核心结构进行演化。使用它们时，架构师应思考：

  1. 变化的触发点是新增、修改还是编排？
  2. 扩展时是否需要修改现有代码（开闭原则）？
  3. 是否存在过度设计？一个简单的 switch 或配置表是否就足够？

第7章 结构组合：灵活的对象编排

7.1 组合模式：树形结构统一处理

组合模式让你能把单个对象和组合对象（容器）统一对待。经典场景：文件系统中的文件和文件夹、UI 中的控件和面板、组织架构中的员工和部门。

代码示例：电商分类树

在电商后台，商品分类可以是叶子节点（具体类目）或树枝节点（包含子类目的大类），客户端无需区分。

类图：

classDiagram
    class Category {
        <<interface>>
        +print()
    }
    class LeafCategory {
        -name: String
        +print()
    }
    class CompositeCategory {
        -name: String
        -children: List~Category~
        +add(Category)
        +remove(Category)
        +print()
    }
    Category <|.. LeafCategory
    Category <|.. CompositeCategory
    CompositeCategory o--> Category : children

架构应用：

  • 菜单/权限树：统一遍历菜单，叶子节点是具体页面，组合节点是菜单项。
  • 微服务组合：在 API 网关中，一个组合响应可能由多个后端服务响应聚合而成，网关就像组合节点，对客户端屏蔽后端服务的树状调用细节。
  • 文件系统：Amazon S3 的对象存储虽然扁平，但模拟文件夹时，逻辑上也是组合模式。

架构思考：组合模式让递归处理变简单，但要注意深度和循环引用。在分布式场景下，树的遍历可能带来 N+1 问题，需要批量加载优化（如一次查询获取所有子节点）。

7.2 装饰器模式：动态附加职责

装饰器模式为对象动态添加功能，而不改变其接口。它是继承的弹性替代方案。Java I/O 流库是经典实例：new BufferedInputStream(new FileInputStream("a.txt"))。

场景：消息通知服务

一个基础的 Notifier 发送纯文本消息，后来需求要求支持加密、压缩、加上签名。用装饰器可以灵活组合这些功能。

类图：

classDiagram
    class Notifier {
        <<interface>>
        +send(message)
    }
    class BaseNotifier {
        +send(message)
    }
    class NotifierDecorator {
        #wrappee: Notifier
        +send(message)
    }
    class EncryptedNotifier {
        +send(message)
    }
    class CompressedNotifier {
        +send(message)
    }
    Notifier <|.. BaseNotifier
    Notifier <|.. NotifierDecorator
    NotifierDecorator <|-- EncryptedNotifier
    NotifierDecorator <|-- CompressedNotifier
    NotifierDecorator o--> Notifier : wrappee

架构实例：中间件管道

在 Web 框架中，对 HTTP 请求/响应的处理可以用装饰器层层包裹。例如，一个基础处理器，外面包上日志、认证、压缩等。这和责任链不同：责任链是“我处理或转发”，装饰器是“我增强后传递”，通常只递归调用一次。

架构师提醒：

  • 装饰器会导致很多小对象，增加内存开销，但通常不是瓶颈。
  • 装饰器与代理的区别：代理在控制访问（如权限、延迟加载），装饰器在增加行为；代理常常被代理对象尚未存在，装饰器始终包裹着真实对象。
  • 当有大量可选功能时，装饰器比继承组合出无限子类要好得多。

7.3 享元模式：共享以节约内存

当系统中有大量细粒度对象且状态可外部化时，享元模式共享内部状态，减少对象数量。

经典案例：字处理器字形对象

字处理器中每个字符如果都是一个对象，内存会爆炸。于是将字符的字体、大小等不变信息作为“内部状态”共享，而位置等可变信息作为“外部状态”在方法传入。

代码示例：云资源图标库

假设一个监控系统要渲染成千上万个云资源（EC2、S3），每个资源有大量相同的图标和颜色，这些可共享。

类图：

classDiagram
    class CloudResourceIcon {
        <<interface>>
        +draw(x, y, id)
    }
    class EC2Icon {
        -type: String
        -iconColor: String
        -shape: String
        +draw(x, y, id)
    }
    class S3Icon {
        -type: String
        -iconColor: String
        -shape: String
        +draw(x, y, id)
    }
    class IconFactory {
        -icons: Map~String,CloudResourceIcon~
        +getIcon(type) CloudResourceIcon
    }
    CloudResourceIcon <|.. EC2Icon
    CloudResourceIcon <|.. S3Icon
    IconFactory ..> CloudResourceIcon

架构应用：

  • 数据库连接池：连接对象的内部状态（JDBC URL、用户名）共享，外部状态（是否空闲）由池管理，连接被复用而不是频繁创建销毁。
  • 常量池：Java 字符串常量池、Integer 的 -128~127 缓存都是享元。
  • 缓存策略：CDN 内容分发，共享相同的静态资源。

技术总监注意：享元会增加代码复杂度，且内部状态必须是不可变的。只有当对象数量巨大且重复时，才值得引入。同时，在分布式系统中，享元一般局限于单机，多实例需考虑缓存一致性。

第8章 状态与生命周期管理

对象的状态变化往往导致复杂的分支逻辑。状态模式、备忘录、命令模式为状态机和可恢复操作提供了清晰的结构。

8.1 状态模式：让对象的行为随状态改变

当对象内部状态改变时，其行为也相应改变，看起来就像换了类一样。状态模式将每个状态封装成独立的类，消除了大量 if-else。

场景：订单生命周期

订单有“待支付”、“已支付”、“已发货”、“已完成”、“已取消”等状态，不同状态下对“取消”、“确认”等操作响应不同。

状态图：

stateDiagram-v2
    [*] --> Pending
    Pending --> Paid : pay()
    Pending --> Cancelled : cancel()
    Paid --> Shipped : ship()
    Paid --> Cancelled : cancel()
    Shipped --> Completed : confirmReceipt()
    Cancelled --> [*]
    Completed --> [*]

架构应用：

  • 工作流引擎：Activiti/Flowable 的核心就是状态模式加流程定义。
  • TCP 连接状态：CLOSED, LISTEN, ESTABLISHED 等。
  • 订单/工单系统：复杂流转用状态模式+责任链或工作流引擎，轻量级则用枚举加 switch 也可以。

设计决策：如果状态很少且行为差异小，使用枚举配合策略（枚举实现策略接口）更简洁。状态多、转换逻辑复杂时，状态模式是首选。

8.2 备忘录与命令模式：撤销、重做与事务回滚

这两个模式经常联手实现可回滚的操作。

8.2.1 备忘录模式：捕获并恢复对象状态

在不破坏封装的前提下，保存对象内部状态，以便以后恢复。

代码示例：文本编辑器的撤销功能

8.2.2 命令模式：将请求封装为对象

将操作封装为对象，从而参数化其他对象，支持排队、日志、撤销。

代码示例：结合备忘录实现撤销的订单修改

类图：

classDiagram
    class Command {
        <<interface>>
        +execute()
        +undo()
    }
    class ModifyOrderAmountCommand {
        -order: Order
        -newAmount: BigDecimal
        -oldAmount: BigDecimal
        +execute()
        +undo()
    }
    class Order {
        -amount: BigDecimal
        +setAmount(BigDecimal)
        +getAmount() BigDecimal
    }
    class OrderCommandExecutor {
        -history: Stack~Command~
        +execute(Command)
        +undoLast()
    }
    Command <|.. ModifyOrderAmountCommand
    ModifyOrderAmountCommand --> Order
    OrderCommandExecutor --> Command

架构应用：

  • 作业调度：命令模式使作业可序列化、异步执行。
  • 分布式事务补偿：每个操作都记录反向命令（撤销），当 saga 事务失败时，按逆序执行 undo 实现补偿。
  • UI 操作回滚：Photoshop 的历史记录栈就是命令+备忘录。

架构师指南：

  • 命令模式会带来大量小类，可以通过 Lambda 表达式简化（如 order.execute(() -> order.setAmount(100))），但会失去 undo 的能力，需要额外封装。
  • 在微服务的 Saga 模式中，补偿事务本质就是命令的 undo 操作，设计时需保证补偿的幂等性。

第7章、第8章小结：

结构组合模式（组合、装饰器、享元）让你能灵活构建对象图，动态添加行为，同时控制内存开销。状态与生命周期模式（状态、备忘录、命令）则为处理对象状态转换和可逆操作提供了坚实的模板。它们共同构成了复杂业务系统的骨架。
