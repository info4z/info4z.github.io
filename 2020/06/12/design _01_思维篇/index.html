一、重新定义设计模式：从代码技巧到架构思想

（一）模式不是银弹——语境、约束与取舍

作为架构师，你拿到一个需求，第一反应不应该是“这里该用哪个模式”，而是：

  1. 上下文是什么？业务多变还是稳定？并发量如何？团队水平怎样？
  2. 约束有哪些？时间、预算、遗留系统、技术栈限制。
  3. 最坏的结果？如果不用任何模式，直接硬写，两年后会发生什么？

【例】策略模式。假设你要做一个消息推送系统，支持短信、邮件、App推送三种渠道。

如果用策略模式，标准实现如下：

对应的 UML 类图

classDiagram
    class NotificationStrategy {
        <<interface>>
        +send(userId, message)
    }
    class SmsStrategy {
        +send(userId, message)
    }
    class EmailStrategy {
        +send(userId, message)
    }
    class AppPushStrategy {
        +send(userId, message)
    }
    class NotificationContext {
        -strategy: NotificationStrategy
        +setStrategy(NotificationStrategy)
        +notifyUser(userId, message)
    }
    NotificationStrategy <|.. SmsStrategy
    NotificationStrategy <|.. EmailStrategy
    NotificationStrategy <|.. AppPushStrategy
    NotificationContext --> NotificationStrategy : uses

架构权衡：

  • 如果这个推送系统未来3年只有这3种渠道，且每种渠道的实现代码不超过20行，引入策略模式就是过度设计。一个简单的 switch 或 if-else 就够了。
  • 但如果渠道会频繁增加、每种渠道的发送逻辑很复杂（比如要调多个外部API、处理限流、重试），且需要运行时动态切换，策略模式的价值就体现出来了。
  • 另外，如果你用的是 Spring 这类框架，结合 @Autowired 自动注入一个 Map<String, NotificationStrategy>，连 setStrategy 都不需要，模式又演化成了依赖注入 + 策略模式。

决策总结：模式的选择取决于变化的来源和频率。变化少，直接用简单实现；变化多，才把变化隔离到策略对象中。

（二）模式的“语言”属性：如何用模式沟通设计意图

当架构师说：“这个支付网关我们采用外观模式加适配器模式，外部银行接口用防腐层隔离。”团队立刻明白：

  • 外观模式：对外提供统一支付接口，隐藏内部调用多个银行、校验、风控的复杂度。
  • 适配器模式：把不同银行的API都转成系统内部统一的请求/响应模型。
  • 防腐层：在调用外部老旧系统时，专门建一层翻译器，不让外部污染域模型。

这就是通用设计语言。你不需要每次画详细类图，一个短语就传达了设计约束和结构。但前提是团队有共同的模式知识。所以技术总监要建立团队模式手册，让“外观”、“策略”、“防腐层”这些词成为日常词汇。

（三）何时引入、何时拒绝一个模式

拿“观察者模式”举例。如果你要做一个订单状态变更后通知物流、积分、消息三个模块的功能。

引入场景：订单模块完全不知道有哪些模块依赖它，将来可能还要加数据分析、审计等。此时用观察者（或发布-订阅）解耦。

拒绝场景：只有两三个下游，且团队规模小、未来半年不会加新下游。直接用方法调用或者异步事件表即可，没必要引入额外的消息队列或事件总线，增加运维复杂度。

架构视角：先简单写出来，当你闻到“代码坏味道”（重复修改同一个地方、多层if-else、类爆炸）时，再重构到模式。

二、设计原则：模式的底层操作系统

模式是原则在特定语境下的实现模板。我们先看最核心的 SOLID 原则，并用代码和图演示。

（一）单一职责原则：SRP

错误示例：一个 UserService 既负责用户注册，又负责发送激活邮件、记录日志。

  • 问题：邮件发送方式变了、日志要写ES、用户存储切到MongoDB，都要改这个类。它因为太多原因而变化了。

【符合 SRP 的设计】拆分职责，并通过协作完成。

类图

classDiagram
    class UserRegistrationService {
        -repo: UserRepository
        -email: EmailService
        -logger: AuditLogger
        +register(username, email)
    }
    class UserRepository {
        +save(user)
    }
    class EmailService {
        +sendActivation(email)
    }
    class AuditLogger {
        +log(message)
    }
    UserRegistrationService --> UserRepository
    UserRegistrationService --> EmailService
    UserRegistrationService --> AuditLogger

架构视角：SRP 不仅是类级别，更是模块、服务级别。微服务拆分时，每个服务应该只有一个变更原因（按业务能力或子域）。

（二）开闭原则：OCP——对扩展开放，对修改关闭

利用策略模式轻松实现。回顾前面的通知系统，如果想增加“微信通知”，只需要新增一个 WechatStrategy 类，无需修改 NotificationContext（假设上下文已设计为接受策略接口）。这就是扩展开放、修改关闭。

关键手段：依赖抽象，而非具体类。把易变的行为抽象成接口。

（三）依赖倒置原则：DIP

高层模块不应依赖低层模块，两者都依赖抽象。

在 UserRegistrationService 中，它依赖的是 UserRepository、EmailService 的接口（如果是面向接口编程），而不是具体实现。利用依赖注入框架，我们可以轻松替换实现。

类图

classDiagram
    class UserRepository {
        <<interface>>
        +save(user)
    }
    class MySQLUserRepository {
        +save(user)
    }
    class MongoUserRepository {
        +save(user)
    }
    class UserRegistrationService {
        -repo: UserRepository
        +register(...)
    }
    UserRepository <|.. MySQLUserRepository : 实现
    UserRepository <|.. MongoUserRepository : 实现
    UserRegistrationService --> UserRepository : 依赖

高层模块 UserRegistrationService 不再直接依赖低层的数据库实现，两者都依赖 UserRepository 接口。这就是依赖倒置：依赖关系倒置了，控制流仍从上到下，但源代码依赖指向了抽象。

（四）原则冲突时的权衡框架

现实中，遵循 OCP 可能会让类数量膨胀；遵循 DIP 会引入大量接口，增加间接性。

架构师要权衡的是：当前成本 vs 未来应对变化的收益。

  • 如果某个模块未来变化可能性极低（如性别枚举），不需要抽象接口，一个枚举足矣。
  • 如果是支付、推送等核心域的边界，必须抽象并严格依赖倒置，并为它们编写契约测试。

技术总监的决策工具：画一个决策矩阵，一边是“变化频度”，一边是“影响范围”。高变化+高影响 → 全力应用设计模式与原则。低变化+低影响 → 简单直接实现。

三、模式分类新维度——从变化与复杂度出发

传统的 GoF 分类（创建型、结构型、行为型）是从代码结构角度划分的。但对架构师来说，更有意义的是按设计意图分类：这个模式解决的是“什么在变化”，以及它如何控制复杂度。我们从三个维度重新组织模式，以便在架构决策时能快速匹配合适的模式。

（一）隔离变化

这类模式的核心思想是：将系统中容易变化的部分封装起来，使其不影响稳定的部分。典型代表：创建型模式、策略模式、桥接模式。

1、创建型模式：隔离“对象的创建方式”

当对象的创建逻辑复杂、创建过程可能变化时（如数据库连接、支付渠道），我们不想让使用方知道具体创建细节。这就是工厂方法和抽象工厂的用武之地。

示例：跨数据库的 DAO 工厂。业务层不关心底层是 MySQL 还是 PostgreSQL，只拿到一个 UserDAO 接口。

类图

classDiagram
    class UserDAO {
        <<interface>>
        +insert(User)
        +findById(int) User
    }
    class MySQLUserDAO {
        +insert(User)
        +findById(int) User
    }
    class PostgreSQLUserDAO {
        +insert(User)
        +findById(int) User
    }
    class DAOFactory {
        <<interface>>
        +createUserDAO() UserDAO
        +createOrderDAO() OrderDAO
    }
    class MySQLDAOFactory {
        +createUserDAO() UserDAO
        +createOrderDAO() OrderDAO
    }
    class PostgreSQLDAOFactory {
        +createUserDAO() UserDAO
        +createOrderDAO() OrderDAO
    }
    class UserService {
        -userDAO: UserDAO
        +UserService(DAOFactory)
    }
    UserDAO <|.. MySQLUserDAO
    UserDAO <|.. PostgreSQLUserDAO
    DAOFactory <|.. MySQLDAOFactory
    DAOFactory <|.. PostgreSQLDAOFactory
    MySQLDAOFactory ..> MySQLUserDAO : creates
    PostgreSQLDAOFactory ..> PostgreSQLUserDAO : creates
    UserService --> DAOFactory : uses

架构决策：如果应用只有一种数据库，工厂就是过度设计。直接 new 对象即可。当系统需要支持多数据库部署，或测试环境需要切换 mock 实现时，工厂的价值就浮现了。此时，依赖注入框架（如 Spring IoC 容器）常常替代手写工厂，但背后思想一致——隔离对象的创建。

2、策略模式：隔离“算法、规则”

前面已演示过消息推送策略。当算法的选择需要运行时决定，且算法族可能增多时，策略模式将易变的算法封装成独立类，使核心逻辑（上下文）稳定。

3、桥接模式：隔离“多维度变化”

当一个类在两个或以上独立维度上变化时（如形状和颜色、消息类型和发送渠道），使用继承会导致类爆炸。桥接将抽象和实现分离，各自独立演化。

示例：消息发送系统，一个维度是消息类型（普通消息、紧急消息），另一个维度是发送渠道（邮件、短信）。如果不用桥接，可能会产生 UrgentEmailMessage、UrgentSmsMessage、NormalEmailMessage、NormalSmsMessage 四个类。用桥接模式，两个维度各自抽象。

类图

classDiagram
    class MessageSender {
        <<interface>>
        +send(content)
    }
    class EmailSender {
        +send(content)
    }
    class SmsSender {
        +send(content)
    }
    class Message {
        #sender: MessageSender
        +Message(MessageSender)
        +send()*
    }
    class NormalMessage {
        +send()
    }
    class UrgentMessage {
        +send()
    }
    MessageSender <|.. EmailSender
    MessageSender <|.. SmsSender
    Message <|-- NormalMessage
    Message <|-- UrgentMessage
    Message --> MessageSender : uses

架构视角：桥接模式在驱动系统平台化时极为有用。比如移动端 App 的抽象层，UI 组件（抽象）与底层渲染引擎（实现）分离，可以让一套 UI 代码适配 iOS 和 Android。当需求中出现“独立演化的两个维度”时，优先考虑桥接，而非继承树。

（二）治理复杂度

当子系统内部极度复杂、对象关系网纠缠时，我们用这类模式提供简化的交互界面，或统一管理复杂的对象结构。典型代表：外观模式、中介者模式、组合模式。

1、外观模式：简化复杂子系统的入口

微服务网关就是最经典的架构级外观。它对客户端提供一个统一的 API，内部将请求路由到多个服务、聚合结果、处理跨领域关注点（认证、限流）。

代码示例：一个简单的订单服务外观，封装了下单过程中的库存检查、支付、物流通知。

序列图

sequenceDiagram
    participant Client
    participant OrderFacade
    participant InventoryService
    participant PaymentService
    participant ShippingService
    Client->>OrderFacade: placeOrder(req)
    OrderFacade->>InventoryService: check(itemId, qty)
    InventoryService-->>OrderFacade: true
    OrderFacade->>PaymentService: pay(orderId, amount)
    PaymentService-->>OrderFacade: true
    OrderFacade->>ShippingService: ship(orderId, address)
    ShippingService-->>OrderFacade: ok
    OrderFacade-->>Client: OrderResult(Success)

架构决策：外观模式本身没有封装子系统，它只是提供了一个更友好的入口。如果客户端需要精细控制（比如先锁定库存、异步支付），就不能强制使用外观，而是允许按需调用子系统。外观在模块化开发、多团队协作时是基础骨架，但要注意防止它变成上帝对象（God Object）。

2、中介者模式：协调多个对象之间的交互

在 GUI 编程中，一个对话框里按钮、文本框的交互逻辑满天飞，中介者可以统一管理交互。在架构层面，消息代理（如 Kafka、RabbitMQ）就是中介者，各服务不直接通信，而是发布消息给代理，由代理路由。

代码示例：聊天室，参与者不直接引用对方，而是通过聊天室发送消息。

类图：

classDiagram
    class ChatRoom {
        <<interface>>
        +sendMessage(from, to, msg)
        +addUser(user)
    }
    class ChatRoomImpl {
        -users: Map~String,User~
        +sendMessage(from, to, msg)
        +addUser(user)
    }
    class User {
        -name: String
        -room: ChatRoom
        +send(to, msg)
        +receive(from, msg)
    }
    ChatRoom <|.. ChatRoomImpl
    User --> ChatRoom : uses
    ChatRoomImpl o-- User : contains

架构权衡：中介者集中管理协作逻辑，简化了对象间的网络连接，但也可能导致中介者本身过于复杂。在微服务中，ESB（企业服务总线）就是这种中介者，过度集中会变成瓶颈和单点。现代架构倾向于使用事件总线（发布-订阅）这种轻量级中介，保持服务的自治性。

3、组合模式：处理部分-整体层次结构

需要忽略单个对象与组合对象之间的差异，统一对待。例如文件系统（文件和文件夹）、UI 组件树、组织架构树。

类图

classDiagram
    class Component {
        <<interface>>
        +operation()
    }
    class Leaf {
        +operation()
    }
    class Composite {
        -children: List~Component~
        +add(Component)
        +operation()
    }
    Component <|.. Leaf
    Component <|.. Composite
    Composite o-- Component : children

架构应用：微服务的分层聚合，或者 API 网关组合后端服务时，往往形成树形调用链。组合模式让我们能用一致的方式处理单个服务调用和多个服务的并行调用与聚合。

（三）组织协作

这类模式定义了对象之间如何交互、如何分配职责，使系统灵活且低耦合。重点：观察者、责任链、发布-订阅。

1、观察者模式：一对多依赖通知

当对象状态变化需要自动通知其他对象时使用。Java 有 Observer 和 Observable（已弃用），但思想延续在事件监听器中。

序列图：

sequenceDiagram
    participant Subject
    participant EmailObserver
    participant LogisticsObserver
    Subject->>EmailObserver: update("SHIPPED")
    Subject->>LogisticsObserver: update("SHIPPED")

架构中的演进：同步观察者可能在通知过程中阻塞主流程，进而演变为发布-订阅模式，借助消息队列解耦，并支持异步、削峰。这就是微服务间事件驱动的基础。

2、责任链模式：请求的流水线处理

在 Web 应用中，过滤器、拦截器、中间件就是典型责任链。每个处理器决定是自己处理请求，还是传递给下一个。

Mermaid 序列图

sequenceDiagram
    participant Client
    participant HandlerChain
    participant AuthHandler
    participant LoggingHandler
    participant BusinessLogic
    Client->>HandlerChain: request
    HandlerChain->>AuthHandler: handleRequest
    AuthHandler-->>HandlerChain: next()
    HandlerChain->>LoggingHandler: handleRequest
    LoggingHandler-->>HandlerChain: next()
    HandlerChain->>BusinessLogic: execute

架构视角：责任链模式允许动态添加或删除处理步骤，非常符合开闭原则。在 API 网关中，一个请求经过限流、认证、授权、审计、路由等一系列链式处理，就是这种模式的具体应用。

本章小结：以变化和复杂度为维度重新分类，能帮助你在架构设计时快速定位模式族群：

  • 隔离变化：当你预见某块代码会频繁改变（算法、创建方式、多维度扩展），用策略、工厂、桥接。
  • 治理复杂度：当你面对复杂的子系统、多对象网状交互或树形结构，用外观、中介者、组合提供秩序。
  • 组织协作：当你需要灵活的解耦通信（通知、请求处理），用观察者/发布-订阅、责任链。
