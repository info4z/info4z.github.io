设计模式概览

一、内功心法

（一）设计模式是什么？解决什么痛点？

1、起源

设计模式最早源于建筑学家克里斯托弗·亚历山大的著作《建筑的永恒之道》。他发现，好的建筑总有某些“模式”可循，比如窗台多高、门开在哪。后来，1994年，GoF（四人帮，Erich Gamma等4位大佬） 把这套思想搬到了软件界，总结了 23种经典模式。

2、官方的定义

定义：在特定上下文中，针对重复出现的软件设计问题，提出的可复用、成熟的解决方案模板。

大白话：就像做菜有“菜谱”。你要做“红烧肉”，不用每次自己瞎琢磨盐放多少，直接照着“菜谱”做，大概率不会翻车。设计模式就是程序员届的“经典菜谱”，解决的是“如何组织类和对象”才能让代码好扩展、好维护。

3、学了有什么用？

  • 告别满屏的 if-else 和 switch。
  • 让代码像“乐高”一样，拆装自如（低耦合）。
  • 看懂Spring、MyBatis等框架源码的必经之路（源码里全是模式）。

（二）UML类图速成：设计模式的“通用语言”

学设计模式，必须会看UML类图。否则你看书上的图就像看天书。记牢以下6种关系（从“强”到“弱”排序）。

1、泛化/继承（Generalization） —— <|-- 空心三角实线

“Is-A”，子类继承父类的所有属性和方法。

生活比喻：狗（Dog）是动物（Animal）。

2、实现（Realization） —— <|.. 空心三角虚线

类实现了接口（契约）。

生活比喻：汽车（Car）实现了“可驾驶”（Drivable）这个能力。

3、组合（Composition） —— *-- 实心菱形实线

“Contains-A” 更强的整体与部分，同生共死（生命周期一致）。

生活比喻：人（Person）和心脏（Heart）。人没了，心脏也就没了意义（被垃圾回收）。

4、聚合（Aggregation） —— o-- 空心菱形实线

“Has-A” 整体与部分，但部分可以脱离整体存在（生命周期不同）。

生活比喻：雁群（GooseGroup）有大雁（Goose）。大雁飞走了，雁群还在，大雁也能活。

5、关联（Association） —— --> 实线箭头

长期持有：A类里面有一个成员变量引用了B类。双方往往是对等的（比如“学生”和“课程”）。

生活比喻：学校（School）里有很多老师（Teacher），学校是长期雇佣老师的。

6、依赖（Dependency） —— ..> 虚线箭头

关系最弱：A类的方法里用到了B类（作为局部变量、参数或调用静态方法）。

生活比喻：人（Person）过河需要用到“船”（Boat），但人不会把船装在自己肚子里，用完了就还回去。

（三）六大设计原则：核心内功，SOLID + 迪米特

这是评价“代码写得好不好”的金标准。我们无需死记，用老板、员工、产品经理的故事讲透。

1、单一职责原则：SRP，“一个人只干一件事”

定义：一个类只能因为一个原因被修改。

生活比喻：公司里，厨师只负责炒菜，司机只负责开车。如果有个“全能员工”既炒菜又开车，还要当保安。那么，炒菜有问题要找他，车坏了也要找他，安保出问题也要找他，那么他就“爆炸”了，根本忙不过来。

代码体现：别把 用户登录 和 用户日志记录 写在同一个类的同一个方法里。

2、开闭原则：OCP，“对扩展开放，对修改关闭”——最重要！

定义：允许新增代码来增加功能，但不允许修改原有核心代码。

生活比喻：苹果手机（iPhone）的充电口是 Lightning。如果每出一代新手机，苹果就要把旧主板的充电模块拆了重新焊接（修改），那太蠢了。苹果的做法是：留一个接口（协议），你插“充电器A”就是普通充，插“快充头”就是快充，我主板代码不用改，外设随便扩展。

代码体现：多态 + 接口。父类引用指向子类对象，新增功能只需新建子类，if-else 全干掉。

3、里氏替换原则：LSP，“儿子能完全替代爹”。

定义：子类可以扩展父类的功能，但不能改变父类原有的功能（不能重写父类的非抽象方法去干别的事）。

生活比喻：你爹会“开车”，你作为儿子应该也会“开车”，而且不能用脚踹着车走（改变父类行为）。如果你把父类的“开车”重写成“开飞机”，那所有用“爹”的地方换成“儿子”就全崩了。

代码体现：重写父类方法时，尽量只做扩展，不做父类逻辑的“颠覆”。

4、接口隔离原则：ISP，“别把大杂烩塞给用户”。

定义：不要强迫客户端依赖它用不上的方法。大接口要拆分成小接口。

生活比喻：去ATM取钱，你只需要“取款”和“查询”按钮。如果ATM屏幕上强行把“修改银行系统内核”、“发放贷款”按钮也塞给你（虽然你点不了），那这个界面就太蠢了。应该把功能拆分。

代码体现：Worker 接口拆成 Workable（干活）和 Eatable（吃饭），别让机器人被迫实现 eat() 方法。

5、依赖倒置原则：DIP，“面向抽象编程，别面向具体”。

定义：高层模块不应依赖低层模块，两者都应依赖其抽象；抽象不应依赖细节，细节应依赖抽象。

生活比喻：电脑（高层）不能直接焊死在主板上一个“某品牌某型号机械键盘”（低层）。电脑应该依赖一个USB接口（抽象）。只要你的设备插头是USB，不管是键盘、U盘还是鼠标，插上就能用。具体设备去实现USB协议。

代码体现：new 关键字是万恶之源！尽量用 接口 作为类型声明。

6、迪米特法则：LoD，“只跟你的直接朋友说话”。

定义：一个对象应当对其他对象有尽可能少的了解，不和陌生人说话。

生活比喻：你想让老板给你涨薪，别直接冲到老板办公室翻他桌上财报（越级且风险大）。你只需要告诉你的直属主管，主管去和老板沟通。你只依赖主管，降低了你和老板（复杂系统）的耦合。

（四）设计模式的灵魂：为什么“组合优于继承”？

很多人喜欢用继承（extends），因为复用代码很爽。但继承有个致命伤：“父类一改，子类全遭殃”（破窗效应），且 Java 是单继承，不够灵活。

组合（Composition）：把一个对象作为另一个对象的成员变量（Has-A）。想要啥功能，直接调用成员变量的方法，或者包装一下。

经典反例：Java 早期 Stack 继承 Vector。Vector 有 add(int index, E element) 方法，导致 Stack 也能在中间插入元素，破坏了“栈”后进先出的特性。如果是组合，Stack内部放一个Vector，只暴露 push/pop，就绝对安全了。

结论：设计模式中大量使用委托（Delegation）和组合，目的就是让代码像“乐高积木”一样，松散地拼在一起，而不是像“俄罗斯套娃”一样死死焊死。

小结

知识点 核心要义 通俗比喻
UML关系 依赖<关联<聚合<组合<实现<继承 短工<长工<师徒<结拜<圣人言<父子
开闭原则（OCP） 新增功能加文件，不改老代码 手机换壳，不改主板
依赖倒置（DIP） 依赖接口，不依赖具体类 电脑只认USB，不认具体设备
组合优于继承 多用“Has-A”，慎用“Is-A” 汽车有发动机，不是汽车继承发动机（荒唐）

思考

1、如果你要写一个“支付系统”，支持微信、支付宝、银行卡。你觉得开闭原则在这里该怎么体现？（提示：策略模式的前奏）

2、画一个“笔记本电脑”和“CPU”、“内存条”、“显示器”的UML类图，它们之间是聚合还是组合？（思考：笔记本坏了，CPU还能拆下来卖二手吗？）

二、创建型模式（Creational Patterns）

这5个模式专门解决 “对象到底该怎么new出来” 的问题。学完这一阶段，你的代码里将再也看不到赤裸裸的 new 关键字满天飞，取而代之的是优雅的“生产流水线”。

可以把这部分内容拆成 “三大核心”（单例、工厂、建造者）重点学习，原型模式一笔带过。

（一）单例模式：Singleton，“独一无二的CEO”

痛点：全局只需要且只能有一个实例。比如：配置管理类、数据库连接池、Spring容器。如果每个人都能随便 new 一个，资源就爆了。

生活比喻：一个公司只能有一个CEO。董事会（系统）只能选出一人，所有人都找他汇报。

1、饿汉式：线程安全，但可能浪费内存

类加载时就把对象造好，像饿死鬼急着吃饭。

  • 缺点：不管用不用，内存都被占了。如果初始化很耗时，会导致程序启动变慢。

2、懒汉式：DCL双重检查锁

需要时才创建，并且为了高并发加了双重锁。—— 面试最常问！

  • 为什么要加 volatile？new LazyCEO() 在 JVM 底层分为三步：①分配内存 ②初始化对象 ③将引用指向内存。如果不加 volatile，CPU 可能优化为 ① → ③ → ②。当线程A执行到③时，线程B来检查 instance == null，发现不为空，直接拿走用了，但此时对象还没初始化完（半成品），程序必崩！volatile 保证必须 ① → ② → ③ 按顺序执行。

3、静态内部类：最优雅、最推荐的方式

利用 JVM 类加载机制，既懒加载又线程安全。

4、枚举实现：最强防破坏

对付反射和反序列化的“终极核武器”（Josh Bloch 大神推荐）。

（二）工厂方法模式：Factory Method，“开闭原则的模范生”

如果你写 Payment pay = new WechatPay();，那代码就写死了。万一要换成 new Alipay();，你得满世界改代码。解决方案：定义一个创建对象的接口，但由子类决定实例化哪个类。工厂方法把 new 的操作延迟到了子类。

生活比喻：你去“必胜客”（抽象工厂）点披萨，你只说要“海鲜披萨”，具体是哪个厨师（具体工厂）烤出来的，你别管，反正最后给你端上来。

场景：实现一个日志记录器

UML 图解（工厂方法）

classDiagram
    class LoggerFactory {
        <<abstract>>
        +createLogger() Logger*
    }
    class ConsoleLoggerFactory {
        +createLogger() Logger*
    }
    class FileLoggerFactory {
        +createLogger() Logger*
    }
    class Logger {
        <<interface>>
        +log(msg)
    }

    LoggerFactory <|-- ConsoleLoggerFactory : 继承
    LoggerFactory <|-- FileLoggerFactory : 继承

    Logger <|.. FileLogger : 实现
    ConsoleLoggerFactory ..> ConsoleLogger : 创建（依赖）
    FileLoggerFactory ..> FileLogger : 创建（依赖）

工厂方法的核心价值：完全符合开闭原则（OCP）。以后新增 KafkaLogger，只需新建 KafkaLogger 类和 KafkaLoggerFactory 类，绝不动 LoggerFactory 和客户端调用逻辑。

（三）抽象工厂模式：Abstract Factory，“生产整套家族产品”

工厂方法只生产一种产品，比如只造轮胎；抽象工厂生产一系列产品族，比如生产轮胎、方向盘+座椅，而且是统一品牌的。

生活比喻：“整车厂”。奔驰工厂产出奔驰轮胎+奔驰座椅；宝马工厂产出宝马轮胎+宝马座椅。你要换车，直接换整个工厂，所有零件全变。

场景：打造不同风格的UI皮肤（Windows风格 vs Mac风格）。

  • 优点：客户端只要拿到 GUIFactory，不管是 Windows 还是 Mac，创建出来的按钮和复选框永远风格统一。增加新风格只需新增工厂，完全 OCP。

（四）建造者模式：Builder，“定制化复杂对象的组装”

当一个类有十几个属性（比如 User 有姓名、年龄、电话、地址、爱好等），构造函数会变得极其冗长且容易传错参数，看得眼瞎。解决方案：链式调用，一步步组装，最后 build()。

生活比喻：组装一台电脑。你必须选 CPU 和主板（必选项），内存、硬盘、显卡是选配。你不必把所有零件塞进一个巨长的构造函数，而是拿着配置单，一项项勾选。

Java 代码：Lombok 的 @Builder 就是这个原理

（五）原型模式：Prototype，“细胞分裂-克隆”

创建一个对象极其昂贵（需要查数据库、算大量数据），但你又需要一个几乎一样的对象。

解决：实现 Cloneable 接口，重写 clone() 方法。

注意：深浅拷贝

  • 浅拷贝：默认，只复制基本类型和引用地址。如果内部有个 List，拷贝对象和原对象共享同一个 List，改一个另一个也变。
  • 深拷贝：递归复制所有引用对象，通常用序列化或 Json 反序列化实现。

小结

模式 一句话场景 关键词
单例模式 全局唯一（配置类、Spring Bean默认单例） 独一无二
工厂方法 生产一种产品，将创建延迟到子类 扩展产品线
抽象工厂 生产一套配套产品（产品族） 换皮肤、换品牌
建造者模式 属性太多，需要链式组装 定制化组装
原型模式 复制昂贵对象（比如缓存中的大对象） 克隆复制

思考

1、Spring 中的单例：Spring 的 @Component 默认是单例的，它是用“饿汉”还是“懒汉”实现的？（提示：Spring容器启动时加载）。

2、重构你的 if-else：假设你现在要做一个“支付路由”，根据 payType 决定 new WechatPay() 还是 new Alipay()。请用 工厂方法 把这个 if-else 干掉。

3、Builder 的滥用：如果一个对象只有 2 个属性，且都是必填，还需要用 Builder 吗？（答：不需要，直接用构造函数，过度设计是反模式）。

三、结构型模式（Structural Patterns）

如果说创建型模式解决的是“对象怎么new”，那结构型模式解决的就是“类和对象怎么组装、拼装”。这7种模式就像乐高积木的7种不同连接件，能让你的代码结构既稳固又灵活。

结构型模式信息量巨大，我把它们分成两组：

  • 高频三巨头（面试最爱）：代理、适配器、装饰器。
  • 架构四基石（提升格局）：外观、组合、桥接、享元。

（一）高频三巨头

这三个模式结构长得极像（都是包一层），但目的完全不同，很多人面试挂就挂在这。傻傻分不清？对比着学！

1、适配器模式：Adapter，“万能转换插头”

痛点：两个接口不兼容，你想用现成的类，但它提供的接口和你期望的完全不一样。

本质：转换。把 A 接口转换成 B 接口，让不兼容的双方能一起工作。

生活比喻：你手机是 Type-C 口，但只有 USB-A 的老充电头。适配器（转接头）插在中间，把 USB-A 转成 Type-C。

经典场景：java.io.InputStreamReader（把字节流 InputStream 适配成字符流 Reader）；Spring MVC 的 HandlerAdapter（把五花八门的 Controller 方法适配成统一的 Handler 执行链）。

代码示例：让火鸡冒充鸭子

2、装饰器模式：Decorator，“无限叠加的皮肤/滤镜”

痛点：你想给一个对象动态地增加额外功能，但用继承会产生“类爆炸”，比如咖啡加糖、加奶、加冰，排列组合会生成无数子类。

本质：增强。不修改原有类，包裹一层给它添加新行为。核心是“增强”，接口必须完全一致。

生活比喻：你买了一杯原味奶茶（核心）。你可以加珍珠（装饰），加布丁（装饰），加芋泥（装饰）。加完还是奶茶，但味道被增强了。

经典场景：java.io.BufferedInputStream 装饰 FileInputStream（增加了缓冲功能）；BufferedReader 装饰 FileReader。

代码示例：奶茶加料

适配器 vs 装饰器（面试死亡辨析）

  • 适配器：接口变了（火鸡变鸭子），是为了兼容。

  • 装饰器：接口不变（奶茶还是奶茶），是为了增强。

3、代理模式：Proxy，“中介/经纪人”

痛点：你不方便直接访问目标对象（比如太耗资源、需要权限校验、需要远程通信）。

本质：控制。代理类 控制 客户端对目标类的访问，可以在访问前后做手脚（日志、事务、权限）。

生活比喻：你想找周杰伦唱歌（目标对象），你不能直接闯他家，得通过他的经纪人（代理）。经纪人决定接不接单，并在中间抽成（增强逻辑）。

Java 实现（Spring AOP 底层核心）：

  • 静态代理：代理类提前写好，编译时就确定。
  • JDK动态代理：目标类必须实现接口，利用反射在运行时生成代理类。
  • CGLIB动态代理：目标类没有实现接口，通过生成目标类的子类（字节码增强）来实现。

代理 vs 装饰器（面试死亡辨析）

  • 装饰器：强调功能叠加，客户端可以灵活组合（点奶茶加小料）。

  • 代理：强调访问控制，客户端不需要知道真实对象的存在，代理替它做决定（找经纪人）。

（二）架构四基石：提升代码格局

4、外观模式：Facade，“一键启动按钮”

痛点：一个业务流程需要调用十几个子系统（下单要调库存、支付、物流、积分），客户端调用起来极其复杂且耦合。

本质：封装简化。给庞大的子系统提供一个统一的、简化的高层接口。

生活比喻：你去餐厅吃饭，你只要对服务员（外观）说“点一份套餐”，服务员就会通知厨师、传菜员、收银员。你不用自己跑去后厨炒菜。

代码示例：秒懂

5、组合模式：Composite，“树形菜单/文件夹”

痛点：你要处理树形结构的数据，但客户端分不清“叶子节点”和“树枝节点”，写代码要一直 if (isLeaf)，极其麻烦。

本质：部分-整体。让客户端用一致的方式处理单个对象和对象组合。

生活比喻：文件夹里有文件（叶子），也有子文件夹（树枝）。你点右键“查看属性”，不管是文件还是文件夹，都能显示大小。

6、桥接模式：Bridge，“跨平台画图”

痛点：一个类有两个独立变化的维度（比如形状有圆形、方形；颜色有红色、蓝色）。如果用继承，要建 RedCircle, BlueCircle, RedSquare等，类会爆炸式增长（M×N）。

本质：抽象与实现分离。把两个维度解耦，用组合代替继承。

生活比喻：遥控器（抽象）和电视（实现）。遥控器的按键逻辑变了，不影响电视；电视换了牌子，也不影响遥控器。

7、享元模式：Flyweight，“池化复用”

痛点：创建了大量细粒度的对象，导致内存耗尽，比如文字编辑器里几万个字符，每个字符都存一份字体对象太浪费。

本质：共享复用。把对象中不变的、可共享的部分（内部状态） 提取出来缓存，变化的（外部状态） 在外部传入。

生活比喻：围棋。棋盘上有无数棋子位置（外部状态），但黑子和白子本质上只有两个对象（内部状态），不断复用这两个棋子对象摆放即可。

Java 经典：String 常量池、Integer 的 valueOf 缓存（-128~127）、数据库连接池。

代码示例：围棋对弈（五子棋同理）

模式 核心关键词 解决什么问题 经典场景
适配器 转换兼容 接口不匹配 插头转换、InputStreamReader
装饰器 动态增强 避免类爆炸，叠加功能 Java I/O 缓冲流、奶茶加料
代理 访问控制 权限、延迟加载、日志 Spring AOP、RMI 远程调用

四、行为型模式（Behavioral Patterns）

前面的创建型管“生”、结构型管“组”，现在进入最核心的“行为型”——它关注的是对象之间如何通信、如何分配职责。行为型模式一共11种，是23种里最多的。

这一阶段拆成两部分：

  • 实战最猛“四天王”：①策略模式 —— if-else 终结者；②观察者模式 —— 发布-订阅核心；③模板方法模式 —— 框架骨架设计；④责任链模式 —— 流水线处理。
  • 剩余“七小只”：最常用、最面试的（状态、命令、中介者），相对冷门的（迭代器、备忘录、解释器），压轴登场的访问者模式（最难懂的模式）。

（一）实战“四天王”

1、策略模式：Strategy，“算法即插即用”

痛点：代码里充斥着 if (type == 1) { ... } else if (type == 2) { ... }。每增加一种支付方式，就要改原来的类，严重违反开闭原则。

本质：定义一系列算法（策略），把它们封装起来，并且让它们可以互相替换。客户端根据上下文选择合适的策略。

生活比喻：你从家去公司，可以步行（策略A）、骑自行车（策略B）、打车（策略C）。目的地一样，但“算法”（交通方式）随时可换。

实战案例：支付路由（干掉 if-else）

2、观察者模式：Observer，“公众号推送机制”

痛点：一个对象状态变了，其他一系列对象都需要自动收到通知。如果用循环硬编码，耦合度极高。

本质：定义一对多的依赖关系。当一个对象（被观察者/Subject）状态发生改变时，所有依赖它的对象（观察者/Observer）都会得到通知并自动更新。

生活比喻：你订阅了某公众号。公众号（被观察者）发布新文章，所有粉丝（观察者）的微信都会收到小红点。你不需要每秒去刷新公众号页面。

手写一个“气象站通知大屏”

  • Spring 中的实现：ApplicationEvent + @EventListener 底层就是观察者模式的完美实现。当某个事件（如用户注册成功）发布后，所有监听了该事件的 Service 都会自动执行后续逻辑（发邮件、送积分）。

3、模板方法模式：Template Method，“标准化流水线”

痛点：业务步骤大体相同，但部分细节实现各异。如果把整个逻辑复制粘贴，维护成本极高。

本质：在父类中定义一个操作中的算法骨架（模板），而将一些步骤延迟到子类中实现。子类可以不改变算法结构，却重定义某些特定步骤。

生活比喻：做咖啡和泡茶步骤都是：①烧水 ②冲泡 ③倒杯 ④加调料。烧水和倒杯是通用的（父类实现），但冲泡和加调料不同（子类实现）。

代码示例：制作饮料

  • Spring 经典实践：JdbcTemplate、RestTemplate 都是模板方法模式的典型。它们把“获取连接、执行SQL、处理结果集”的骨架固定，你只需实现 RowMapper（映射具体的返回对象）这个可变步骤。

4、责任链模式，Chain of Responsibility，“层层审批/过滤器”

痛点：一个请求需要多个对象处理，且处理顺序/权限是动态的。如果把所有判断写在一个类里，又变成“上帝类”。

本质：将请求沿着一条链传递，直到有对象处理它为止。每个处理器都有机会处理，也可以选择推给下一个。

生活比喻：公司请假审批。组长批 3 天以内，经理批 3~7 天，CEO 批 7 天以上。你提交申请后，从组长开始传，组长批不了就自动往上推。

代码示例：请假审批流

  • 经典框架应用：Spring Security 的过滤器链（Filter Chain）、Netty 的 Pipeline 都是责任链模式。每个过滤器只做一件事（认证、授权、日志），顺序可插拔。

模式 核心关键词 解决什么问题 经典场景
策略模式 算法互换 干掉 if-else，运行时切换算法 支付路由、优惠券计算
观察者模式 发布订阅 一对多状态同步 消息队列、GUI事件监听、Spring Event

1、策略 vs 状态（提前预告下节课内容）：策略是“外部主动切换算法”；状态是“对象内部状态变化导致行为自动变化”。你觉得支付场景用哪个合适？

2、组合设计：如果让你把 策略模式 + 工厂模式 + 责任链模式 结合，写一个“复杂的风控审核系统”，每个风控规则（比如地域、金额、频次）串成链，最后用策略模式处理通过/拒绝，你会怎么构思？

（二）其余“七小只”

5、状态模式：State，“对象心情决定行为”

痛点：一个对象在不同状态下，行为完全不同。如果用 if (state == 1) ... else if (state == 2) ...，当状态增多时，代码膨胀且极难维护。

本质：将状态封装成独立的类，把行为委托给当前状态对象。状态的变化由状态对象自身决定，实现“状态驱动行为”。

生活比喻：人的心情。心情好时（状态A），别人打招呼你微笑回应；心情差时（状态B），别人打招呼你翻白眼。同样是“打招呼”这个动作，结果因“状态”而异。

策略模式 vs 状态模式（面试高频终极辨析）

对比维度 策略模式 状态模式
谁来决定切换 客户端主动调用 setStrategy() 切换 状态对象内部自己决定切换到下一个状态
类的关系 上下文和策略是单向持有 上下文和状态双向关联（状态持有上下文的引用）
意图 解决算法互换（一次性选择） 解决状态转移（状态随流程变迁）
生活比喻 出行选“地铁”或“公交”，外部决定 红绿灯：红灯→绿灯→黄灯，自动流转

代码示例（订单状态机：已下单 → 已支付 → 已发货 → 已完成）

  • 核心价值：新增一个“退款中”状态，只需新建类，修改相关状态的转移逻辑，绝不污染订单主类。

6、命令模式：Command，“遥控器的按键封装”

痛点：客户端发起请求，需要知道接收者是谁、怎么调用，耦合过高。且希望支持“撤销/重做”或“日志记录”。

本质：将请求（包括参数和接收者）封装成一个对象（Command），让调用者和接收者彻底解耦。

生活比喻：餐厅点餐。你（调用者）把菜单（命令对象）交给服务员，服务员交给厨师（接收者）。你不需要知道厨师是谁、用什么锅炒，你只需要点菜。

代码示例（智能家居遥控器）

  • 进阶：如果再给 Command 加一个 undo() 方法，就能完美实现 Ctrl+Z 撤销功能。

7、中介者模式：Mediator，“机场塔台协调”

痛点：多个对象之间互相引用，形成 网状结构（多对多），改一个牵连所有，耦合度爆表。

本质：引入一个中介者，将网状结构变成星型结构（一对多）。所有对象只跟中介者通信，由中介者协调。

生活比喻：机场塔台。所有飞机（对象）不能随意互相喊话，必须听从塔台（中介者）的调度，塔台决定谁起飞、谁降落。

  • 经典场景：MVC 中的 Controller 就是 Model 和 View 之间的中介者。

8、访问者模式：Visitor，“最烧脑但最优雅”

痛点：一个稳定的数据结构（比如一堆形状：圆、方、三角），但操作（算法）经常变化（画图、导出JSON、计算面积）。如果用 if (type) 去判断，每次新增操作都要改数据结构类。

本质：将数据结构与操作分离。定义一个访问者，为数据结构中的每个元素提供一个 visit 方法。数据结构只接收访问者，不关心访问者具体干什么。

生活比喻：医生上门体检。你家（数据结构）里有客厅、卧室、厨房（固定元素）。医生（访问者）来体检，在客厅量血压，在卧室测视力，在厨房查燃气。下次换个电工（另一个访问者）来，同样走一遍房间，做不同的操作。

代码示例（形状导出不同格式）

优点：新增“导出JSON”功能，只需新建 JsonExportVisitor，Shape 体系一行不改。
缺点：如果数据结构经常变（比如新增一个 Triangle），则所有 Visitor 接口都要改，所以只适合数据结构稳定、操作多变的场景。

剩余3个模式（极速通关）

模式 一句话解释 经典场景
迭代器模式 提供一种方法顺序访问集合元素，而不暴露内部结构。 Java 的 Iterator、List.iterator()
备忘录模式 在不破坏封装的前提下，保存对象内部状态，以便恢复（存档/读档）。 游戏存档、JPA 实体快照
解释器模式 定义一种语言的文法，并提供一个解释器来处理该语言中的句子。 正则表达式、SQL 解析（极少手写，了解即可）

思考：检验是否通透

1、状态 vs 策略：一个“红包活动”系统，有“未开始、进行中、已过期”三种状态。用户点击“领取”按钮，行为随状态变化。请问用状态还是策略？

五、大型企业架构

闯过 GoF 23 座大山，现在你已经是“模式熟练工”了。但真正的战场在大型企业级架构——分布式、微服务、高并发场景下，经典 GoF 模式需要升级换代。

（一）控制反转（IoC）与依赖注入（DI）—— “不要找，要等”

GoF对应：这是对依赖倒置原则（DIP） 和工厂模式的终极升华。

痛点：传统代码里，每个类都自己 new 依赖（Service service = new ServiceImpl();），导致耦合如钢筋水泥，改一个依赖全局大地震。

本质：好莱坞原则——“Don‘t call us, we‘ll call you（别找我们，我们找你）”。对象不主动去创建依赖，而是由外部容器（Spring）在运行时把依赖“注入”进来。

生活比喻：以前你找对象得自己满大街相亲（主动new），又累又容易踩坑。现在你注册了“世纪佳缘”（Spring容器），填好要求（接口），平台直接给你匹配好对象送到你面前（依赖注入）。你只管“坐享其成”。

代码示例（Spring 的 @Autowired 底层干了啥？）

底层原理：Spring 启动时扫描所有 @Component，把它们注册到一个 Map（容器） 里。当遇到 @Autowired 时，Spring 从 Map 里找到匹配的类型，通过构造器注入或Setter注入赋值进去。这个过程中用到了工厂模式 + 反射。

（二）MVC模式（Model-View-Controller）—— “各司其职的分层艺术”

GoF对应：观察者模式（View监听Model变化） + 策略模式（Controller选择View） + 中介者模式（Controller作为V和M的中介）。

痛点：没有分层时，HTML（视图）、SQL（模型）、业务逻辑（控制）全揉在一个JSP里，改一个按钮颜色可能搞崩数据库。

本质：分离关注点。

  • Model（模型）：数据 + 业务逻辑（POJO + Service）。
  • View（视图）：展示层（JSP/Thymeleaf/JSON），只负责渲染。
  • Controller（控制器）：接收请求，调用Model，返回View（路由转发）。
flowchart LR
    Client[浏览器/App] -->|HTTP请求| Controller
    Controller -->|调用| Service[Model/Service]
    Service -->|查/改| DB[(数据库)]
    DB -->|返回数据| Service
    Service -->|封装Model| Controller
    Controller -->|选择View| View[Thymeleaf/JSP/JSON]
    View -->|渲染响应| Client

现代变种：前后端分离后，View层退化为JSON序列化器，Controller直接返回 Restful API 数据，前端框架（React/Vue）接管视图渲染。

（三）DDD战术模式（领域驱动设计）—— “让代码表达业务”

痛点：很多项目把业务逻辑全塞进 Service 里，导致Service变成几千行的“上帝类”，且数据库表结构直接暴露给上层，业务规则散落各处。

本质：DDD（Domain-Driven Design）不是新设计模式，而是一套架构方法论，它教我们如何用代码精确地模拟真实业务领域。其中几个核心战术模式与设计模式深度融合：

DDD战术组件 通俗解释 对应设计模式/思想
实体（Entity） 有唯一ID、会变的对象（如：订单、用户） 普通Java类，但封装了业务行为
值对象（Value Object） 没有ID，用属性值来判等，不可变（如：金额、地址） 不可变模式 + 工厂模式
聚合（Aggregate） 一组相关对象的“家族树”，外部只能通过“聚合根”访问内部 组合模式 + 外观模式
仓储（Repository） 屏蔽数据库细节，让上层感觉像在操作“对象集合” 工厂模式 + 适配器模式
领域事件（Domain Event） 业务发生的重要事情（如：订单已支付） 观察者模式（发布/订阅）

（四）响应式模式与回压（Backpressure）—— “抗住流量洪峰”

痛点：传统同步阻塞（Tomcat每个请求占一个线程），高并发下线程耗尽，服务器直接宕机。异步非阻塞能抗更高并发，但生产者发送数据太快，消费者处理不过来会内存溢出。

本质：响应式流（Reactive Streams） 定义了 4 个接口（Publisher, Subscriber, Subscription, Processor），核心是订阅者主动向发布者“拉取”数据（回压），而不是发布者无脑推。

生活比喻：你在食堂打饭。不是厨师（发布者）把做好的菜一股脑全塞给你（无回压，你会撑死）。而是你拿着餐盘（订阅者），说“给我一勺”（request(1)），你消化完了再喊“再来一勺”（回压机制）。

（五）并发编程模式—— “多线程下的安全盾牌”

1、不变模式：Immutable Object，“免锁的终极方案”

本质：对象一旦创建，内部状态永远不变。多线程访问无需加锁，绝对安全。

经典案例：String、Integer、LocalDate。

实现要点：所有字段 final，不提供 setter，对可变引用做防御性拷贝（如 Collections.unmodifiableList()）。

2、线程安全持有者模式：Thread-Safe Holder

本质：利用 ThreadLocal，每个线程持有自己的一份副本，避免竞争。这其实是享元模式 + 单例模式在并发场景的变种。

经典场景：SimpleDateFormat 不是线程安全的，用 ThreadLocal 包装，每个线程用各自的格式化器。

小结：架构级模式速查

模式/思想 核心关键词 解决什么问题 落地框架
IoC/DI 容器托管、自动装配 解耦对象依赖关系 Spring Framework
MVC 分层分离 请求路由、视图解耦 Spring MVC / Struts
DDD战术 充血模型、聚合、仓储 复杂业务逻辑的领域建模 无特定框架，思想落地
响应式+回压 异步非阻塞、订阅者拉取 高并发下资源保护 Reactor / WebFlux
不变模式 final字段、防御拷贝 线程安全无锁化 String、LocalDate
ThreadLocal 线程副本隔离 线程私有变量 数据库连接池、日期格式化

思考

1、IoC容器是工厂模式的超级变种。你能说出 Spring 的 ApplicationContext 和简单工厂（new XXXFactory()）的3点本质区别吗？（提示：生命周期管理、循环依赖、AOP增强）

2、DDD聚合设计：在“电商订单”业务中，Order（订单）和 OrderItem（订单明细）是聚合关系。请问：修改一个 OrderItem 的商品数量，应该通过 Order 的哪个方法去操作，而不是直接 orderItem.setCount()？为什么？

3、回压实战：假设你负责一个消息推送系统，上游（业务系统）每秒发送 10 万条消息，下游（用户手机推送网关）每秒只能处理 5000 条。如果不做回压会怎样？用响应式模式如何解决？

（一）源码中的设计模式（面试硬通货）

面试官最爱问：“请举例说明JDK或Spring中哪里用到了设计模式？” 下面给你一张保命速查表，背下来就能镇场子。

1、JDK 源码中的经典亮相

设计模式 JDK 经典体现 通俗解释
单例模式 java.lang.Runtime.getRuntime() JVM运行时环境，全局唯一
工厂方法 java.util.Collection.iterator() 每个集合（ArrayList/HashSet）返回自己的迭代器
适配器 java.io.InputStreamReader 字节流 → 字符流
装饰器 java.io.BufferedInputStream 给FileInputStream加缓冲功能
策略模式 java.util.Comparator 集合排序时传入不同比较器（Comparator），算法互换
模板方法 java.util.AbstractList 定义了add()等骨架，子类重写具体细节
观察者 java.util.Observer / Observable（虽已过时，但经典） 状态变更通知
迭代器 java.util.Iterator 遍历集合的统一方式
享元模式 Integer.valueOf(int) 缓存 -128~127 小数字复用对象，省内存
代理模式 动态代理 java.lang.reflect.Proxy JDK原生动态代理

2、Spring 框架中的“模式博物馆”（架构师必答）

设计模式 Spring 中的体现 面试说辞
工厂模式 BeanFactory / ApplicationContext 整个IoC容器就是超级工厂，负责创建和管理所有Bean
单例模式 @Scope("singleton")（默认） Spring容器中的Bean默认就是单例
代理模式 AOP（动态代理） 切面增强（事务、日志）底层就是JDK Proxy或CGLIB
模板方法 JdbcTemplate、RestTemplate 固定骨架（获取连接/执行SQL/释放资源），我们只需实现RowMapper回调
观察者模式 ApplicationEvent + @EventListener 发布事件（如用户注册），监听器自动异步执行发邮件/送积分
适配器模式 HandlerAdapter（Spring MVC） 把各式各样的Controller方法适配成统一的执行链
策略模式 ResourceLoader 根据路径前缀（classpath:/file:/http://）选择不同资源加载策略
责任链模式 Spring Security 过滤器链（FilterChain） 请求按顺序经过层层过滤器（认证→授权→日志）
装饰器模式 BeanWrapper 动态给Bean添加属性编辑器（类型转换）
桥接模式 JDBC驱动（其实是Spring整合时对DriverManager的封装） 抽象（操作）与实现（具体数据库驱动）分离

面试金句：Spring 本质上是一个 “设计模式集大成者”，学透Spring = 学透设计模式的实战用法。

（二）如何识别“坏味道”并用模式重构？

光会背模式不行，得能闻到代码里的腐臭味，才能对症下药。

四种典型的代码坏味道及重构方案

坏味道（代码症状） 病根 用什么模式救 重构动作
1. 巨长的 if-else / switch 算法或类型判断散落各处 策略模式 + 工厂模式 把每个分支封装成独立策略类，用Map<类型, 策略>获取
2. 创建对象极其复杂（构造函数参数超过5个） 构造函数重载灾难 建造者模式（Builder） 引入Builder内部类，链式调用 .setA().setB().build()
3. 一个类继承了多个层级（继承链过深） 滥用继承导致脆弱性 组合 + 装饰器/代理 将继承改为成员变量持有（Has-A），用装饰器动态增强
4. 修改一个类引发多个类连锁反应（God Class） 职责过多，违反单一职责 外观模式 / 中介者模式 拆分类，或用中介者协调复杂交互

重构实战小案例（干掉 if-else）

（三）设计模式滥用警示：过度设计 = 灾难

记住金句：“设计模式是用来解耦的，不是用来炫技的。” 滥用比不用更可怕。4种必须喊停的滥用场景

1、只有2个分支，也强行上策略模式

  • 错误：if (isVip) 两种情况也建两个类、一个工厂、一个Context。
  • 正确：直接用 if-else 或三元运算符，简单就是美（KISS原则）。

2、对象只有2个必填属性，强行上Builder

  • 错误：new User.Builder("张三", 25).build() 比 new User("张三", 25) 啰嗦10倍。
  • 正确：Builder只用于 >4个参数 或 大量可选参数 的场景。

3、为“将来可能会变”提前做过度设计

  • 错误：“将来可能会换数据库，我先上一套抽象工厂+适配器”。结果项目到死都没换。
  • 正确：YAGNI原则（You Ain‘t Gonna Need It） —— 只解决当前明确的需求，只重构被真实变化反复折磨的地方。

4、责任链滥用导致调试地狱

  • 错误：一个请求经过20个Filter，出了问题不知道哪个环节改了数据。
  • 正确：责任链长度控制在 5-7个 以内，超过则考虑拆分子链或引入编排中心。

（四）终极实战：简易支付网关，5大模式大合唱

最后，我们把 工厂、策略、责任链、观察者、模板方法 全部整合到一个真实的业务场景中：聚合支付网关。

业务需求

  1. 支持微信、支付宝、银行卡支付（策略模式）。
  2. 下单前要做风控校验（责任链模式：黑名单校验 → 限额校验 → 合规校验）。
  3. 创建支付记录并调用第三方通道（模板方法：固定骨架，具体支付细节子类实现）。
  4. 支付成功后，发送MQ/事件通知订单系统和积分系统（观察者模式）。
  5. 客户端获取支付方式时，用工厂模式屏蔽具体策略类。

核心代码骨架（Spring Boot 风格）

看到了吗？ 5大模式在一套系统里各司其职、互不干扰，新增支付方式只需加一个类，改一个配置文件，核心代码一行不动——这就是设计模式的终极威力！
